## The decision rule gives: memory follows the artifact — stop

- **It does not stay within a few MB of a fixed size.** `sync accept` peaks at 52 MB for 7.4 MB, 110 for 26, 210 for 52, **411 for 105**: **3.9–4.2× the artifact** for many small objects (7× at 10,000 small patches), and **5.8× for a single 100 MiB file** (606 MB). The earlier 11 MB flat (250 and 1,000 patches, 0.2–0.7 MB artifacts) was the small end of the same line.
- **`bundle import` on the same content is flat at 12 MB** for 100 one-MiB objects: `accept` is 34× its peak there.
- **For a single large object, memory follows the object, in both:** `bundle import` of one 100 MiB file peaks at **405 MB (3.9× the object)**; `accept` at 606 MB (5.8×; 1.5× the bundle's). So "follows the artifact" is `accept`'s alone for many objects; "follows the object" is both importers' for one big one. (I did not fix the bundle's; it is a finding, below.)
- **At the defaults** (256 MiB total, 256 MiB per object) the same lines give **about 1.0 GB for a 256 MiB artifact of small files and 1.5 GB for one 256 MiB file** (an extrapolation of the measured ratios, not a run). The cap bounds it; a forge accepting from many senders at once multiplies it.

## Where the memory is held (call sites; from the code and the RSS timeline, `timeline.txt`)

1. **`prikk-cli/src/sync.rs:222` `read_bounded_file`**: the whole artifact into one `Vec<u8>` before anything is checked. 1×. (The timeline: RSS climbs to ≈ the artifact size with no `.prikk` file open.)
2. **`patch_exchange/accept.rs:148` → `artifact.rs:322` `decode_exchange_artifact` → `decode_envelope_section`**: every patch, blob, claim and tag decoded into an owned `ObjectEnvelope` (payload copied out of the buffer), all kept in `DecodedExchangeArtifact` until the end. 1× more. (RSS ≈ 2× the artifact, still before the store is opened: ≈ 200 MB at b100.)
3. **The other ≈ 2× appears after the repository is open (the `active`, `containers` and `recovery` handles are held) and before the objects are written** (b100: 211 → 411 MB within 135 ms, then flat through the 1.9 s of writing; s100: stepwise 300 → 606 MB before the blob container is first opened for writing). I did not instrument this window, so I can name its place (`accept.rs` Phases C/D, between `ObjectReadSnapshot::open` at the closure check and `ObjectWriteSession::open` at line 333; the objects are then written one by one through `write_object_under_held_lock`, lines 415 and 449) but **not the allocation**; an allocation profile is the first step of any streaming design. `ObjectWriteSession` itself does not hold them: `bundle import` uses the same session and is flat.
So the three: the file, the decoded copy, and a still-unattributed ≈ 2×, all alive at once. The writes (lines 415, 449) are bounded by one object each; the retention is in the decode, not the write.

## Other facts the measurement turned up (reported, not fixed)

- **Fsyncs, 0.57.0 → main (P2a):** directory syncs fall from 60,170 to 14 at 10,000 patches (6 per patch → a constant); **file syncs stay 4 per patch (40,108)**. Total 100,278 → 40,122. At 10,000 patches `sync accept` takes about 63 s on both builds, so on this (loaded) machine the wall is dominated by 40,000 file syncs, not by the directory syncs P2a removed; I make no claim from wall here.
- **`bundle import` of a single large object peaks at ≈ 4× that object** (405 MB at 100 MiB), although it streams many small ones flat. A candidate for the ROADMAP, not part of P3.
- **`sync accept` reads nothing from the store** (≤ 2.7 MB) and writes exactly the artifact's bytes (+ framing); its cost is memory and file syncs, not store reads.
- **planeter's promise is untouched:** no `accept` code changed; its write order (patches and blobs, then AUTHOR key material, then claims and tags) and exit 1 on a write error are as before.

## For you

1. **P3 does not close "not built, by measurement": memory follows the artifact** (and, for one big file, the object). Streaming `accept` is yours to rule, under P3's original conditions: one validator, pass 2 matching pass 1 per object, the interrupted-accept guarantee, and planeter's promise. What a streaming design starts from: copies 1 and 2 above are removable by reading and decoding frame by frame; copy 3's allocation is not yet identified.
2. **Whether the 256 MiB default bounds are right for a forge** given ≈ 4–6× memory (1.0–1.5 GB at the cap). A lower default total bound would be a cheaper mitigation than streaming, and is a behaviour change; I did not test it.
3. **`bundle import` of one large object** (405 MB at 100 MiB): into the ROADMAP or P3's design, your call.

## Owner's word on the three questions (relayed in chat, after the report)

The owner asked for the three to be reviewed against the fundamental philosophy, then wrote **"All the recommendations of yours are accepted."** This is the owner's word to the architect, not a handoff: **I am not building until a streaming section is written.** The recommendations accepted:

1. **Streaming `sync accept`: build it.** `bundle import`'s two-pass shape reused (no second decoder); pass 1 reads the whole artifact before signatures are checked (the author keys sit at its end), pass 2 writes, matching pass 1 object by object. **Find the unattributed ≈2× first** (design step 1: if it is in the validation phases, streaming the decode alone does not remove it). Fixed: the artifact format, planeter's write order and exit 1 for a write error, the state a killed accept leaves. **Claim no more than it delivers:** memory follows the largest object, not the artifact (one 100 MiB file stays several times its size, as in `bundle import`'s 405 MB); the docs and CHANGELOG say so. **Closing target:** peak RSS no higher than `bundle import`'s on the same content (≈12 MB for 100 × 1 MiB), writes and fsyncs unchanged; one 100 MiB file no worse than `bundle import`'s 405 MB.
2. **The 256 MiB default bound is not lowered.** It stays the sanity ceiling once streaming lands; `PRIKK_EXCHANGE_MAX_BYTES` is the operator's control today. **A docs sentence and a line in planeter's release letter** (yours): until streaming lands, `sync accept` holds about 4–6× the artifact in memory. If streaming is not built in 0.58.0, the bound is revisited then.
3. **The single-large-object peak is recorded as a measured row under RFC 158** (large objects: streaming and chunk manifests), not as a separate item: `bundle import` 405 MB and `sync accept` 606 MB for one 100 MiB file, one root cause.
