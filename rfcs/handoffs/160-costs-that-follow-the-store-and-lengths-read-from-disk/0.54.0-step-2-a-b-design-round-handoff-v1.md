## Part 2A — the files at a point (90 min, report `0.54.0-step-2-A-design-report.md`)

**What the command is** (planeter's letters of 2026-10-15, 2026-10-17 and 2026-10-18; our replies of 2026-10-15 and
2026-10-18, all under `.git-exclude/upstream/planeter/`):
- **It reads a point:**
  - a ref;
  - a block id;
  - or **one** pending accepted claim, meaning its claimed parent's files plus that claim's patches.
- **It writes that point's files into a new, empty folder** outside the repository, with no history. An existing folder
  is refused.
- **Never:**
  - several claims together;
  - a claim applied onto a moved base;
  - a merge;
  - a stream;
  - a second command.

**What happens today, to start from:**
- **The read path:** `cat` and `tree` use `replay_point_for_read_only_report` (`patch_replay.rs:558`). It rebuilds the
  whole tree from the nearest snapshot, holding every file's bytes in `ChainReplay.files` (`patch_replay/anchor.rs:53`).
- **The cost of that:** measured on 0.52.0 and 0.53.0, about 2.07× the live content with one version, and 1.04× the
  repository with four.
- **Snapshots:** every block sealed since **0.43.0** carries one when it is due: a ref's first block and every 64th
  (`checkpoint_due`, `block_state.rs:337`).
  - Import validates a snapshot that is present, but never requires one.
  - **So history sealed before 0.43.0, or crafted history, can have no snapshot in reach.**
- **A pending claim's state:** look at how `seal_from_accepted.rs` derives a claim's state, and say whether 2A can
  share that derivation read-only.

**Answer from source, with figures:**
1. **Cost.** What writing a point costs (bytes read, peak RSS, wall time, release build, idle machine, at least two
   samples):
   - (i) on a checkpoint;
   - (ii) 63 blocks after one;
   - (iii) with no snapshot in reach.

   Measure today's read path and at least one option that does not hold every file's bytes. For example: apply patches
   by blob id, and read only the final blobs, written straight to the target. **For (iii), the design bounds the cost
   or refuses by name,** and states which.
2. **Size first.**
   - A form that reports the point's **file count and total bytes** and writes nothing.
   - `--max-bytes` and `--max-files` refuse the whole point, by name, before the first write.
   - **For each limit, state whether it holds before the cost** (nothing large read yet) **or only before the write.**
     planeter asked for exactly this distinction.
   - Per-file sizes only if they cost nothing extra.
3. **Memory.** Peak RSS as a measured function of the point's size, in a form the command's documentation can carry.
4. **It touches nothing in the repository:** no worktree, marker, cache or lock writes.
   - **Document its locking:** does it take a read lock, and what happens if a writer runs at the same time?
   - **It reports whether the point's block is replay-confirmed,** as `checkout --snapshot-materialize` prints
     `provisional:`.
5. **Writing safely from possibly untrusted patches** (a pushed claim):
   - checkout's path-safety rules (`docs/src/reference/path-safety.md`) apply, with no escape from the target;
   - non-ASCII paths and symlinks refuse the whole point;
   - **all-or-nothing:** a refused or interrupted run leaves no partial folder. Say how: a temporary sibling renamed at
     the end, or another way, and what a crash leaves.
6. **`cat` and `tree`** (the owner's Decision 3): can they share the new read path **with output identical byte for
   byte,** and are they cheaper on it? Answer with the figure. If not, they stay as they are.
7. **The read gate:** a row for the new command on the content and history axes, with its expectation and the reason.
8. **The name, flags and output fields** proposed, as a proposal only. `--format json` follows the conventions the
   other read verbs use.

**Constraints:**
- **no format change;**
- **no cache becomes authority** (RFC 162);
- **the command never writes into the repository.**

## Part 2B — received content that no ref reaches (90 min, report `0.54.0-step-2-B-design-report.md`)

**What happens today** (measured by the architect on 0.53.0, 2026-10-19):
- A bundle imported under a key the repository never adopts leaves `verify` reporting *"repository has
  publication-trust issues"*.
- **`current-state.md` says** that replacing the received pointer with a later sound import leaves the earlier objects
  in place, still failing that check, and that no command removes stored objects.

**Why `verify` keeps failing:**
- `verify_objects` (`verify/objects.rs:152`) trust-checks stored objects through `PublicationTrustVerifier`, whether or
  not anything reaches them. Confirm this from source.
- RFC 164 Rule E's walk (`verify/reachability.rs`) already computes reachability from committed state, but it is used
  only to classify a Block's own dangling references.

**The external architect's shape** (external review 027, `.git-exclude/upstream/external-architect/receive/027-…/`):
1. **B1, the read-side rule first:** a stored `RefState` or `Block` that nothing reaches is a remnant.
   - **"Nothing reaches it"** means no local ref, received pointer or queued patch, and no sealed block reached from
     them: the Rule E roots and expansion.
   - `verify` **names and counts** it as a warning, and **no longer fails publication trust on it**.
   - **Nothing is deleted.**
2. **B2, then a narrow removal verb,** kept independent: `prikk received remove <remotes/…> [--plan-only]`.
   - It is recorded in the recovery log (RFC 168) as one run, so it can be restored byte for byte.
   - It refuses while anything else reaches those objects.
   - It never applies to local refs.

**Answer from source:**
1. **B1's rule, exactly:**
   - which object types it covers;
   - how the trust verdict becomes reachability-aware without weakening it for anything reachable;
   - **the security property in one sentence:** *trust never becomes "unreachable, so ignored" through a crafted
     pointer, and never becomes "reachable" through an object's own claims.* Show which code enforces each half.
   - Rule E's existing comment says the walk is computed from committed state only, never from an object's claims. Say
     whether B1 needs anything more.
2. **The walk equals the store's reachability on every `matrix.py` state** (the external architect's script, latest copy
   under `.git-exclude/upstream/external-architect/receive/030-ack-0-53-0-released-verified/reproduce/`, the same one 0.53.0's
   P3 ran). Say how this will be tested.
3. **The crafted-archive receiver:**
   - an import that tries to make an untrusted object reachable through a received pointer, a tag, or a
     `previous_ref_state_id` chain must still fail trust;
   - **list each shape and its outcome under B1.**
4. **B2's design:**
   - what exactly it removes: the received pointer, its received-index record, and only the objects nothing else
     reaches afterwards;
   - how the recovery log records the run, and how a restore puts every byte back;
   - its refusals: a local ref, a reached object, a concurrent writer;
   - its crash behaviour at every write ordinal, as a case table for both parities (the case-table rule);
   - **its race with ordinary writers:** `commit`, `seal`, `sync accept`, `bundle import`. A repair verb is a writer.
   - **B2 ships in 0.54.0 only if this design is clean** (the owner's Decision 2): a case table, restorable from the
     recovery log, refusing while anything reaches the objects. **If it is not clean, say so plainly.** It then moves
     to 0.55.0 without holding the release.
5. **What `current-state.md` and the 0.52.0 Security entry will say** under B1, and under B1 + B2.

**Constraints:**
- **no format change** unless the report shows one is needed, with the reason;
- **no cache becomes authority;**
- **every refusal today is still a refusal for anything reachable,** shown by the case table;
- **B1 writes nothing.**
