## P5a: the batch's memory (90 min, stop at 120). DONE (accepted 2026-11-25, `.git-exclude/reviewed/0.59.0-P5-part-a-review-v1.md`)

1. **S1, the retained checkpoint states (a released defect; `### Security` when removed).**
   - **Where:** `BatchFold::fold` clones the whole state at every checkpoint (`block_state/batch_fold.rs:111-112`). `SealBatchPlan::fold`
     keeps every clone until the loop reaches its block (`seal_from_accepted/batch.rs:425-439`, drained by `take_step_for`).
   - **The size:** in a tree that grows a path per claim it is about 0.81 × claims² bytes. M1 measured 20 MB at 5,000; the architect's
     out-of-sample check is 15.9 and 16.7 MiB at 2,000.
   - **Design how the fold holds one state at a time:**
     - **(i)** the loop re-derives a checkpoint's state when it reaches it (at most 64 claims' patches onto the running state); or
     - **(ii)** a second running fold advances with the loop and writes each snapshot from its own state; or
     - **(iii)** anything better.
   - **For each:**
     - the time it costs, measured or bounded;
     - what it reads;
     - that the bytes sealed are identical (the snapshot's entries and texts);
     - and **the case table's crash row:** a kill mid-batch must leave what K's `sync seal` sweep accepts today, so the sweep must stay X 0
       unchanged.
   - **The target:** the growing shape becomes linear. Say the predicted per-claim slope.
2. **S2/S3, the object index held 3.9× its one-copy size: count first.**
   - **The measurement:** live allocations per stack (the one-line probe change M1 named), at fixed 10,000.
   - **Then say which it is:**
     - capacity slack from an amortised `extend`;
     - copy-on-write copies kept alive by older snapshots (`index_snapshot.rs:171`, `release_kept` at `:286`);
     - or both.
   - **The answer:** (a) needed, with its bound per stored object; or (b) not needed, and what dropping it changes.
3. **S4/S5, every accepted claim in the repository, read to seal one batch** (`enumerate_stored_claims`, the claims index):
   - **The question:** can the order-ambiguity check (`refuse_if_order_ambiguous_indexed`) and the parent check
     (`require_parents_reached`) read only the claims that name the batch's blocks or patches?
   - **Answer it with the check's own argument,** not by assumption: what a claim outside that set could change in the decision.
4. **S8, the decoded envelope of every ref-log record** (about 1.4 KB per sealed block, ten sites): which of it the publication
   precondition needs (`ensure_publication_precondition_with_replay`, `refs.rs:276`), and what the rest is.
5. **CPU:**
   - **The cost:** each claim's state root is computed over every path (`entries_from_state`, `compute_state_root` per claim), so claims ×
     paths in time as well. The growing 10,000 run took 274 s against 63 s fixed.
   - **The options:**
     - an incremental root (which leaf changed, and the path to the root); or
     - an argument, with numbers, that the cost is acceptable where it matters (the 256 MiB artifact's 360,000 claims).
   - **Time cost matters,** so say which, with the measured slope.
6. **The docs sentences** for what the batch genuinely needs: from M1, about 125 B per stored object for the index and about 0.6 KB per
   accepted claim. They are written at P5's close, **with the numbers P5 leaves**. Here, say what they will be under each option.
7. **Stop at P5a's report.** The architect rules each item: build, do not build, or a question for P5b.

## P5a1: the fold holds one state at a time, and the claim drops its read snapshot first (90 min, stop at 120). DONE (`bdbf7c65`, accepted 2026-11-25; `.git-exclude/reviewed/0.59.0-P5-part-a1-review-v1.md`)

**A released, peer-driven defect: `### Security`.**
- **The cause:** in a tree that gains a path per claim, 0.58.0's fold kept every checkpoint's whole state, about 0.81 × claims² bytes
  (M1, P5a).
- **The architect's check:** your prototype gave 27.6 → 24.5 MiB at 3,000 claims, with byte-identical containers, and a control that
  moved the hash.

1. **S1, option (iii):**
   - The loop advances a second running fold, and writes each checkpoint's snapshot from that fold's own state.
   - **The up-front pass is apply-only** (`apply_candidate_patches`, no entries, no root). It runs **only when the target branch is the
     current one,** since its only product is the final state the in-the-way check reads.
   - **Fail-safe as today:** a running-fold error at a claim seals it, and every later claim, from disk.
   - **No `P5A_*` switch, timer or probe survives into the build.**
2. **S2, the scoping fix:** `read_snapshot` and `fresh` are dropped (or scoped) before `ObjectWriteSession::open`
   (`seal_from_accepted.rs:211`, `:214`, `:436`), so a write's `Arc::make_mut` no longer copies the whole index.
3. **The steps buffer:** no capacity kept after the pops (`shrink_to_fit`, or a `Vec` read by index).
4. **Proof that the plan is used:** a counter (test-visible) of the claims sealed from the plan against those sealed from disk. A normal
   batch asserts **zero from disk**, in both shapes.
5. **Tests:**
   - **byte-identity:** the containers after a growing batch and after a fixed one equal today's, on the current branch **and on
     another branch** (the path the prototype did not run). Built from one base, sealed with the old code and the new;
   - **a control** that drops a snapshot entry, and must make the identity fail;
   - **memory:** a test-visible assertion that the fold holds at most one checkpoint state at a time, not a timing;
   - **the real-kill sweeps:**
     - `sync_seal_batch` stays X 0, unchanged;
     - **new, `sync_seal_checkpoint`:** a base of 62 sealed blocks, then a batch of 3 claims, so the batch crosses a checkpoint. X 0 on
       today's code first, then on the build. **Not** the 66-claim, 3,106-ordinal shape, which costs minutes on CI.
   - Red controls: the old retention back; the snapshot kept across the write session.
6. **Measured on the final build,** with planeter's `sealmem.sh grow` at 1,000, 3,000 and 5,000 claims, and the fixed shape at 10,000:
   VmData and CPU against today. **The growing slope should be linear.** Say the measured per-claim slope, and whether 10,000 was run.
7. **CHANGELOG:**
   - **`### Security`:** the curve measured at 1,000 to 10,000, and the extrapolation labelled.
   - **The reach:** a forge sealing a peer's batch in a tree that gains paths.
   - **The way round in earlier versions:** none measured beyond one point. Say so.
8. **The rules as in step 0:**
   - 15 gates;
   - a final build from the committed tree into a fresh target directory;
   - stage by path;
   - the ten output constraints (no output should move: say so, measured).

## P5a1b: the state the check judges is exactly 0.58.0's, and `seal_checkpoint` crosses a checkpoint (60 min, stop at 90). DONE (`a9fe0167`, accepted 2026-11-25). **G3 is next:** `rfcs/handoffs/147-refusal-visibility/0.59.0-G3-one-next-step-handoff-v1.md`; then P5a2

1. **The healed-collision corner, made exact (P5a1 report §5.2).**
   - **Why:** `judged_state`'s own documented policy (`seal_from_accepted/batch.rs:598-602`) is that the in-the-way check never pre-empts
     an earlier claim's valid seal. In the corner (a claim collides, and a later claim heals it), the quick way judges the state after the
     last claim and can refuse over a path created after the colliding claim.
   - **Do:**
     - keep the collision index incrementally across the apply-only pass: the folded keys of the state, with counts;
     - each claim checks only the paths its patches create or rename into, and a removal decrements;
     - **the state judged is the state after the last claim whose state does not collide,** exactly 0.58.0's.
   - **The proof:** a differential test against `refuse_colliding_entries` over the full entries, per claim, over generated batches:
     - collide then heal;
     - collide and stay;
     - a rename into a collision;
     - the removal of one of a pair;
     - Unicode-folding pairs.
   - **A red control:** the healed case judged at the end.
   - **If `refuse_colliding_entries` is a rule over the whole state that cannot be checked per changed path, stop and say why.**
   - The cost: say it, measured on the growing 5,000.
2. **`seal_checkpoint` crosses a checkpoint (P5a1 report §5.1).**
   - **The fact:** checkpoints are Blocks 1, 65, 129, … (`checkpoint_due`). `seal_checkpoint` seals the 64th, which is not one.
   - **Do:**
     - `gens 64`, so the shape seals the 65th;
     - **a pin in the shape** that the sealed Block carries a snapshot;
     - the durability row says "the 65th block (a checkpoint: a ref's first Block and every 64th after it)".
     - **Every other "64th" assumption:** `grep -rn 64th` over the code, tests and `docs/src`, and the shapes' `gens` counts. Fix or list
       each one. `current-state.md:478` gets the exact wording.
   - The sweep is run on the new shape and its numbers are reported. X 0 is expected; anything else is a finding.
3. **The rules as in step 0:**
   - 15 gates;
   - a final build from the committed tree into a fresh target directory;
   - stage by path;
   - `docs/src` with the docs gate after the last edit;
   - no output change (say so, measured).

## P5a2: the ref log, summarised per ref by the hold, never re-walked (90 min, stop at 120). DONE (`160ebf01`, accepted 2026-11-25; `.git-exclude/reviewed/0.59.0-P5-part-a2-review-v1.md`)

**Why** (P5a §4, measured):
- a claim makes **three whole-log walks**: `ensure_no_incomplete_publication` twice (`seal_from_accepted.rs:198`, `:295`), and the
  publication's own precondition plus `classify_state`;
- each walk decodes every `RefUpdatePayload` of the ref and re-checks the whole chain;
- **together they are 53% of a 10,000-claim fixed-tree `sync seal`** (31.6 of 60 s), and they grow with the log;
- the decoded envelopes are about 1.4 KB per sealed block of memory.

0. **First, G3's last surface** (G3 review, ruling 2): `doctor --rebuild-pointer-index`'s refusal (`pointer_rebuild.rs:387`) asks
   `queue_sealed_into_lead`. In the combined state it names `prikk seal --allow-no-audit` first, as every other surface does; otherwise
   `ref complete`, as today. A test from the swept state, and a red control.
1. **What the precondition needs, per ref** (P5a §4):
   - the newest record's `new_ref_state_id`, and the one before it;
   - whether the last record equals the publication's `ref_update` (`exact_last`);
   - that the chain is sound to the tip: each `old_ref_state_id` is the previous `new_ref_state_id`, `update_seq == index + 1`,
     `created_at == 0`, and `ref_name` matches;
   - that nothing in the log is damaged.
2. **The summary, kept by the hold** (beside `kept_ref_log`):
   - **what it holds, per ref:** the count, the last two ids, the last record's envelope (for `exact_last`), and "sound to here";
   - **how it is kept:** extended by the appended tail only, under the kept replay's existing staleness protocol (stat, canary, tail);
   - **no record's envelope is kept but the last.**
3. **It fails closed: this is a safety check.** Any doubt falls back to today's full walk:
   - a stat or canary mismatch;
   - a tail that does not extend the summary's last record;
   - a record the summary cannot classify;
   - another process's write;
   - a format-7 duplicate record.
   - **Say each fallback in the code,** and count them in a test-visible counter.
4. **A differential test:** the summary's answer against the full walk's, for every state the case tables name:
   - a sound log;
   - a torn tail;
   - a lead (pointer ahead by one);
   - a damaged interior record;
   - another ref's records interleaved;
   - a duplicate record of one id;
   - an empty log;
   - a log that another process extends between two claims.
   - **The same decision and the same refusal text,** in every case. Red controls: a summary that skips the chain check; one that trusts a
     stale tail.
5. **The real-kill sweeps stay X 0, unchanged:** `sync_seal_batch`, `sync_seal_checkpoint`, `seal`, `tag create`, `branch create`,
   `ref complete`.
6. **Measured on the final build,** with the fixed shape at 10,000 and growing at 5,000:
   - the three walks' share before and after;
   - the time per claim;
   - **VmData;**
   - **containers byte-identical.**
7. **CHANGELOG:** a `### Changed` entry (a performance change, with its numbers), if no output moves. Measure that none does.
8. **The rules as in step 0:**
   - 15 gates;
   - a final build from the committed tree into a fresh target directory;
   - stage by path.

## P5a4: the parent check remembers what it proved reached (60 min, stop at 90). DONE (`88e486c8`, accepted 2026-11-26; `.git-exclude/reviewed/0.59.0-P5-part-a4-review-v1.md`)

**Why** (P5a3 §4, counted):
- `parent_reached_visiting` walks every claim's chain to the root: **50,015,000 steps for planeter's 10,001-claim chain, n²/2.**
- It is most of the CPU `sync seal` still takes in that shape.

1. **The cache:**
   - **Only "reached":** a block proven reached against the plan's history. A block not reached is never remembered (a later claim can
     reach it).
   - **The validity is "the history only grows within one plan":**
     - the cache is keyed to the history it was proven against (the plan's tip, or a history generation);
     - **it is dropped whenever the plan re-walks its history** (the ref moved under the batch), when the plan is abandoned, and when a
       claim is sealed from disk instead of from the plan;
     - any doubt drops it, so it fails closed to today's walk.
2. **Tests:**
   - **P5a3's differential test** (`the_subset_decides_as_the_full_read_does`), run with and without the cache: the same decision and the
     same refusal text;
   - **a chain batch's step count, asserted linear** (a test-visible counter);
   - **a ref moved between two claims of one plan:** the cache is dropped, and the decision equals the walk's.
   - **Red controls:**
     - the cache kept when the tip moves;
     - an unreached block remembered;
     - the cache never dropped.
3. **Measured,** planeter's fixed 10,000 and the chain shape: CPU before and after, and containers byte-identical. **The real-kill sweeps
   stay X 0, unchanged.**
4. **CHANGELOG:** `### Changed`, with its numbers, if no output moves (measure that none does).

## P5b1a: the two-piece append with `writev` (60 min, stop at 90). DONE (`595b5933`, accepted 2026-11-26; `.git-exclude/reviewed/0.59.0-P5-part-b1a-review-v1.md`)

## P5b2a: the lock files' durability, designed (90 min, stop at 120). DONE (accepted 2026-11-26; `.git-exclude/reviewed/0.59.0-P5-part-b2a-review-v1.md`: option C, built with P5b2b's hold)

**Design only. Nothing built; stop at the report.**

**Why** (P5b1 §2, measured):
- every lock is created with the durable create (`lock.rs:315`, `create_new_file_required`: write, file sync, directory sync) and
  removed with a directory-synced removal (`Drop` → `remove_file_cleanup_best_effort`): **three syncs per acquisition;**
- `sync seal` takes 5.77 acquisitions a claim, so **17.3 of its 25.4 syncs a claim are lock files;**
- on a disk, nearly all of a batch's time is syncs: about 28 minutes against 8 s on tmpfs for planeter's fixed 10,000.

1. **Every reader of a lock file, enumerated from the code:**
   - `unlock` (listing, liveness, `--yes`, `--force`);
   - `doctor`'s held-lock finding;
   - F2's in-flight judge (`another command is publishing …`);
   - the interrupted markers of `branch switch` and `checkout`, and whether any use a lock's presence;
   - the import journal's gate;
   - the recovery log;
   - every place that treats a lock left after a crash as **evidence** of an interrupted operation rather than as an exclusion;
   - **the boot-id and liveness judgement** (a lock from before a reboot).
   - For each: what it concludes from the lock, and whether a non-durable create or removal changes that conclusion **after a power
     loss** (not a process kill: the page cache keeps it then).
2. **The case table, after a power loss:**
   - a lock absent where a process had created it;
   - present and whole;
   - present with an empty or short body (the body's write not durable);
   - **present where a process had removed it (the removal not durable).**
   - **Each row ends typeable:** what `unlock`, `doctor` and the next writer say, and the command that clears it. **No row is a state no
     command clears,** and none lets two writers in at once.
3. **The design, if the table holds:**
   - lock files created and removed without their syncs;
   - **the exclusion itself is the page-cache `O_EXCL` create, unchanged;**
   - what still syncs, and why.
   - **Windows:** its lock create, its removal, and what each costs there.
   - **The cross-version row:** a 0.58.0 binary meeting a lock 0.59.0 left after a power loss.
