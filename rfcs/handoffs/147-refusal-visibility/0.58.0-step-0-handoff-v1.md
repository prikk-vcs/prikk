## Part 0a: `--yes` refuses an *unknown* holder, and `prikk-store`'s `prikk-ffi` edge is target-gated (60 min, stop at 120)

**What external review 050 §2 measured** (0.57.0 candidate; real `prikk bundle import` holders frozen with `SIGSTOP`):
the judge never says "does not appear to be running" of a live holder. But in four shapes it answers *unknown*:
- another PID namespace;
- a fresh PID namespace judging an outside holder;
- a time namespace with an offset;
- a changed machine identity, as on a shared drive.

**In all four, `unlock --lock <path> --yes` cleared the lock of a live, frozen holder, exit 0.** Containers, sandboxes and
shared drives produce *unknown* every time.

**The architect measured one more *unknown* on the published 0.57.0** (`~/.pgtmp/ink-asks/probe6.log`, `probe7.log`):
**an empty `active.lock`** reads "unknown: the lock body is incomplete: still being written, or damaged".
- `commit` refuses while it is there.
- `--yes` clears it, and so does `--force`.

The lock is created exclusively and then written (`lock_holder.rs:24`), so an empty lock can belong to a writer that is
starting now.

**The rule** (owner-accepted 2026-11-14):
1. **`--yes` clears a lock only when its holder "does not appear to be running".** *Unknown* is refused like *appears
   running*. **`--force` is the only way to clear either.**
2. **A typed `yes` at the prompt follows the same rule as `--yes`.** They are one answer given two ways. A rule that let
   the prompt clear what `--yes` refuses would be two rules. If you find a reason the prompt should differ, stop and ask.
3. **The refusal states the reason the judge gave** (the `liveness_words` text: another namespace, another machine, an
   older prikk, an incomplete body). It names `prikk unlock --lock <path> --force`, and what `--force` risks. It is one
   function beside `refuse_live_holder`, or that function generalised. There are never two refusals that word the same
   risk differently. Exit 1, before anything is asked or written.
4. **A lock written by 0.56.0 or earlier is *unknown*,** so it now needs `--force`. That is intended. The release notes
   say so (see "Docs" below).

**Then:**
- **Tests,** through the binary, one per *unknown* reason the suite can make on Linux:
  - an incomplete body;
  - an older body;
  - a changed machine identity;
  - another PID namespace, where the runner allows `unshare`; otherwise say so and skip with the reason.

  Each asserts that `--yes` exits 1, the lock is byte-identical, and the refusal names the reason and `--force`. `--force`
  clears each one. "Does not appear to be running" still clears with `--yes`. The typed-`yes` path is tested once with

  ("a holder that appears running is refused unless --force") says what is refused. `doctor`'s `PRIKK-DOCTOR-HELD-LOCK`

- **CHANGELOG:**
  - a `### Changed` entry naming the change of behaviour;

## Part 0c: the reference says when `block_seals` is whole (45 min, stop at 90)

**What the architect measured** on the published 0.57.0 (`~/.pgtmp/ink-asks/probe4.log`, `probe5.log`), with three sealed
blocks:

| repository | `verify` exit | `block_seals` | `failed_objects` |
|---|---:|---:|---|
| sound | 0 | 3 | none |
| one Block record damaged (one byte) | 1 | **2** | one `block`, `corrupt` |
| one ref log damaged (one byte) | 1 | 3 | none |
| cleanup-pending | 1 | 2 of 2 | none |

`block_seals` comes only from the objects stage (`verify.rs`, `verify_objects`). That stage is first, so it is never
halted.

**The rule:**
- **One sentence in `commands.md`'s `block_seals` item:** the list holds every sealed Block reached from committed state
  when `stages` reports `objects` as `evaluated` and `failed_objects` is empty. A damaged Block is named in
  `failed_objects` and is not in the list.
- **No new field.** A consumer reads both conditions from fields it already has.
- **No claim wider than the mechanism.** Before writing "every", measure a damaged RefState and a damaged Patch.
  - If a damaged RefState hides blocks while `failed_objects` lists it, the sentence holds as worded.
  - If something hides a Block with `failed_objects` empty, stop and ask.
- **A test that holds the sentence:**
  - the damaged-Block row (`block_seals` loses it, `failed_objects` names it);
  - a sound repository, where the counts agree with `log`'s blocks.

  Cite it from the sentence, the way the assurance table (A) will cite tests.
- **The red control:** make `failed_objects` drop a corrupt Block, and name the assertion that goes red.
