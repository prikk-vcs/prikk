## Part 0a: `sync seal` onto a branch the receiver does not hold (90 min, stop at 180)

**What the architect measured** on the published 0.56.0 binary (2026-11-08, `branch2.sh` in the architect's scratch;
the shape the dev team found at 0.56.0 P3b):
- **The old repository:** `heads/main` has 3 sealed commits. `heads/feature` is `branch create --from heads/main`
  plus one commit adding `f.txt`. Its tree holds `a.txt` and `f.txt`.
- **The new repository** (fresh `setup`, the same keys): `heads/main` is carried with `sync have` / `build` /
  `accept` / `seal`, correctly. Then `heads/feature` is carried the same way, **without `branch create` first**.
- **`sync seal heads/feature --claims …`** prints, for the three claims `heads/main` already sealed, `heads/feature
  was already fully sealed -- no-op`. That is false: `heads/feature` does not exist. It then seals `f1`'s patch onto
  the unborn `heads/feature` as a new root.
- **The result:** the new `heads/feature` holds only `f.txt` (`tree`: 1 entry, `log`: 1 block). Every exit code is 0,
  and `verify` exits 0. **The branch silently lacks its earlier files.**

**The rule** (gates refuse; a writer never guesses at history):
1. **"Already fully sealed" is judged against the target ref's own history:** blocks reachable from its current tip.
   Blocks some other ref sealed don't count. The message must never say a ref holds something it does not.
2. **`sync seal <ref>` refuses before any write** when a claim it would seal names a parent block that `<ref>`'s
   current tip does not reach. This includes an unborn `<ref>` with a claim whose parent is not the empty root.
   - The refusal names the claim, its parent block, and the way out:
     `prikk branch create <ref> --from <a ref that reaches the parent>` when a local ref reaches it.
   - **When no local ref reaches the parent,** the way out must still be something the user can type. Say that block
     `<id>` is not held here, name the commands that carry the branch it belongs to first (`prikk sync have …`, then
     `build`, `accept`, `seal`), and then name the `branch create`. A refusal that only says "not held" names nothing
     to do.
   - **No new `refusal-v1` id, and no `--format json` for `sync seal` in this part.** `sync seal` has no JSON
     surface today, so an id would be invisible, and a name beside `extract`'s `claim-parent-not-sealed` would be
     two near-identical words for different conditions. Whether every refusal gets an id is J's question (0.59.0).
     Classify it as 0.56.0's in-the-way refusals are classified: exit 1 and `error: precondition not met:`.
   - Nothing is written: `.prikk` byte-identical, and `verify` clean afterwards.
3. **The documented way still works:** `branch create heads/feature --from heads/main` first, then the same carry,
   gives the old repository's tree and block ids (the architect measured this route at 0.56.0 P3b).

**First, a case table, before any code,** measured on 0.56.0 and then on the fix. The rows are the target ref's state
against the claims' parents:
- unborn, with a root claim (must work as today);
- unborn, with a non-root claim (this defect);
- an existing ref whose tip reaches the parent (works as today);
- an existing ref on another line;
- an existing ref behind the parent.

For each row, say what 0.56.0 does and what the rule does. **If any row's right answer is not "refuse" or "as
today", stop and ask.**

**Then:**
- **Tests:** one per row, through the binary. The shape above must refuse with `.prikk` byte-identical. The
  documented route gives identical block ids and tree. A red control: name which row each assertion fails without the
  change.
- **Docs:** the sync guide (`docs/src/guide/…` for sync, wherever a second branch is carried) states the `branch
  create` step. `commands.md` gets the refusal. `troubleshooting.md` gets an entry for the new message.
- **CHANGELOG:** a `### Fixed` entry. It is a released defect, measured on 0.56.0 with the measurement stated.

## Part 0b: a damaged commit-index cache, and the owed sentence (60 min, stop at 120)

**What external review 046 §4 measured** (on 0.55.0 and the 0.56.0 candidate alike; not re-run by the architect): one
plausible wrong hex digit of a recorded content hash in `.prikk/cache/commit-index.v1` makes `commit --from-worktree`
of an unrelated new file refuse with `integrity error: EditText requested for unchanged text`. That names no path
and no way out.
- `verify` exits 1 and names the path and the cache.
- `doctor` exits 0, silent.
- `status` and `diff` show nothing.
- Deleting the cache file cures it. Their `ci.sh` is in
  `.git-exclude/upstream/external-architect/receive/046-…/reproduce/`.

**The rule** (a cache only saves work; it never changes an answer or blocks a writer):
1. **Reproduce it first,** on the published 0.56.0 binary, with `ci.sh`'s shape.
2. **`commit` treats a cache entry whose recorded hash disagrees with the content as a miss:** re-hash the path, and
   rewrite or drop the entry. It never fails because of a cache entry.
   - If the disagreement can only be seen at the point the error is raised today, the fix goes there. Say where.
   - Name every other reader of `commit-index.v1` (`status`, `diff`, `worktree-status`, …), and say which trust an
     entry without re-hashing and what each does with a damaged one.
3. **`verify`'s exit code stays as it is.** Per the DC-56 cache-validity specification
   (`rfcs/handoffs/DC-56-commit-full-tree-scan-compliance/cache-validity-specification-v1.md` §5–§6), the stat trust
   is an accepted heuristic, and `verify`'s divergence check is the designed detector for an entry that would make
   `commit` silently skip a real change. It must keep failing.
4. **`doctor` reports the same divergence, and both name a way out the user can type,** as a prikk command, not "delete
   a file under `.prikk`":
   - name the existing command that drops or rebuilds the cache, if there is one;
   - if there is none, propose the smallest one and stop for the architect's ruling before building it.

   Name the `doctor` code you choose.
5. **One paragraph, no code:** how often the accepted residual risk of §5 can occur on the filesystems we support
   (nanosecond mtime on ext4, btrfs, APFS and NTFS; FAT's 2 s). Also whether refusing to record an entry whose mtime
   is not older than the index write (git's racy-entry rule) would close it at no hot-path cost. That decides whether
   it becomes a ROADMAP row.

**Tests:**
- the hex-digit shape: before the commit, `verify` (exit 1) and `doctor` both name the divergence and the way out;
  `commit` succeeds and authors only the new file; afterwards `verify` is clean;
- a red control.

**CHANGELOG:** a `### Fixed` entry (a released defect, 0.55.0 and 0.56.0).

**The owed sentence**, in the same part:
- **In `docs/src/reference/data-model.md`, one sentence:** signatures and RefUpdates have a `created_at` field, every
  current writer sets it to 0, and so no block, patch or ref record carries a time.
- Cite the writers you checked (`maintainer_signing.rs`, `author_signing.rs`, `seal_from_accepted.rs`, …), and grep
  for any writer that sets a non-zero value. If one exists, stop and ask: the sentence would be false.
- If a guide page describes what a block records, give it the same sentence.
