## What is true today (measured by the architect on `1f314053`, 2026-11-09)

- **`log --format json`:** each block has `block_id`, `kind`, `parent_count`, `patch_count`, `patch_messages`,
  `previous_ref_state_id`, `ref_state_id`, `required_attestation_count`, `rollback_block`, `rollback_patch_count` and
  `update_seq`. There is no parent id and no sealer.
- **`verify --format json`:** the top-level keys are `active_sessions`, `schema_version`, `stages`,
  `unreached_objects` and `verdict`. There are no sealers, no item counts, no failed objects.
- **`branch create heads/f --from <block id>`** refuses: "--from ref … does not resolve to a published ref".
  `tag create --target <block id>` accepts the same id (stikk's reading: `tag.rs` `resolve_target_block`, `branch.rs`
  `resolve_published_target`).
- **`cat --path x.sh --output <file>` of a 0755 file** writes 0644.
- **`cat --path nope --format json`** prints the text refusal, not a `refusal-v1` document.
- **`sealed_by` is shipped** in `bundle preview` as "a plain list of signing key ids, reported but never trusted". Its
  per-signature outcomes are in a separate, additive `sealed_by_signatures` (`commands.md`, the `bundle preview`
  section).
- **`parent_block_ids` is the Block's own stored field, sorted by object id.** So a merge's parents carry no "first
  parent" order (`data-model-lifecycle.md`).

### S5b: the owner's philosophy check (2026-11-10, "verify carefully they also meet my fundamental philosophy")

The design holds:
- one verb, beside the commands that own the queue;
- named exactly, newest only, healthy queue only;
- every crash state has an honest classification;
- the undo refuses once anything has changed;
- `--plan-only` equals the run.

The architect's check found **five places where it must also hold.** They are part of S5b; measure each first:

1. **Re-running the same command after a crash finishes it.** The natural thing an interrupted user does is type
   `prikk uncommit <id>` again.
   - **Crash after the WAL cut, before the witness:** today this reads as row 5, `…ACKNOWLEDGED-LOSS`, "no longer
     present at all". That is alarming after a deliberate removal. A re-run of `uncommit <id>` must finish it
     (rewrite the witness, then the record) and say "already taken out of the queue; finished".
   - **Crash after the witness, before the record:** the stale record gives the misleading "behind … 0 file(s)". A
     re-run brings the record up to date.
   - **A re-run after completion:** "not queued", naming the run id.
   - **`doctor`'s recommendation for row 5** adds one true clause: if this follows an interrupted `prikk uncommit`,
     running it again finishes it. The recovery log is never authority, so the re-run recognises the state from the
     WAL and witness, and the log only names the run.
2. **The next commit must author the same meaning as the removed patch, or the plan says what will differ.** The
   worktree keeps the files, but not everything a patch records can be read back from the worktree. A **rename**
   recorded through `prikk mv` would come back as delete + create, a new node, so the file's identity is lost.
   - Inventory every operation kind and say, for each, whether the next `commit` re-authors it.
   - Where it would not, prefer restoring the intent (for a rename, the `declarations` entry) as part of the run, in
     the write order, with a crash row of its own.
   - If that does not fit, stop and ask, rather than shipping a silent change of meaning.
3. **A binary patch's blob.**
   - `verify` reports an unreached blob as "blob … is reached by nothing in this repository -- its publication trust
     was not checked; the bytes stay, and no command removes them yet" (measured on `received remove`). For a blob
     that `uncommit` left, "publication trust" is beside the point: a blob is not published under a seal. Measure
     the line for an uncommitted blob and make it true for blobs.
   - The plan says that committing the same file again reuses it, and that otherwise it stays as that warning until
     reclamation exists.
   - **The architect reports this residual to the owner:** a warning that no command clears. It is the same class
     that `received remove` and `--discard-damaged-commits` already leave, and reclamation is a ROADMAP item.
4. **After removing the only queued patch, the session reads as an empty queue,** byte for byte the state `seal`
   leaves (`ref-name`, `witness`), not an anomaly. Add the case where the queue targets a ref other than the current
   branch (`commit --ref`): the record's `queued_fold` is rewritten only where it applies.
5. **No piecemeal JSON.**
   - `uncommit` has the other repairs' text report shape and exit codes (0 done, 1 refused, 2 usage), and no
     `--format json` until J (0.59.0) decides the tier, as ruled for 0a.
   - The release letter tells inklkunn this.
