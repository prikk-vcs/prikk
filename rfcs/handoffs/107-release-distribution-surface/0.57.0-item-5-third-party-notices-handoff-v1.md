## What is true today (measured by the architect, 2026-11-10)

- **Every release archive ships `prikk` and `LICENSE` only** (`release.yml`: `tar -C stage -czf … prikk LICENSE`
  for the three tarballs; `Compress-Archive … prikk.exe, stage/LICENSE` for the zip).
- **Both PKGBUILDs install only `LICENSE`** (`tools/release-policy/templates/prikk.PKGBUILD.txt` and
  `prikk-bin.PKGBUILD.txt`: `install -Dm644 LICENSE "$pkgdir/usr/share/licenses/prikk/LICENSE"`).
- **The resolved graph's licences** (`cargo metadata`, every package including development dependencies) include
  `BSD-3-Clause`, `Unicode-3.0`, `Zlib`, `MIT` and `MIT-0` beside Apache-2.0. BSD-3-Clause, MIT, Zlib and
  Unicode-3.0 each ask for their notice in binary distributions.
- **The linked set depends on the target:** `windows-sys` only on Windows, `libc` directly only on macOS (`prikk-ffi`).

## The part

1. **Measure first, and report:**
   - the set of crates **linked into the `prikk` binary** for each of the four release targets: normal dependencies
     only (`cargo metadata --filter-platform <triple>` and the resolve graph's dependency kinds), never development
     dependencies, never build-script or proc-macro-only crates;
   - for each crate, its SPDX expression, and whether its published package contains a licence file (in
     `~/.cargo/registry/src`);
   - the crates that have none, by name.
2. **One generated file, committed: `THIRD-PARTY-NOTICES`** at the repository root.
   - It holds, for every crate linked on any release target: the name, the version, its SPDX expression, the targets
     that link it, and the full text of each licence file its package ships.
   - It is generated by `tools/release-policy` from `cargo metadata` and the registry sources. **No new tool or
     dependency.**
   - It is deterministic: sorted by name, then version.
   - Committing it makes it reviewable, puts it in the source tarball the `prikk` PKGBUILD builds from, and lets the
     archives copy it.
3. **A gate (the 15th):** regenerate and compare.
   - It fails when the committed file differs, so a dependency change cannot land without its notices.
   - It fails when a linked crate ships no licence file, naming the crate. **Stop and ask** if any crate is in that
     state today, rather than inventing a fallback text.
   - Give it a red control: add a dependency without regenerating.
   - It goes into `scripts/gates.py`, and into CI as the other policy gates are. Say which job runs it.
4. **Ship it everywhere `LICENSE` goes:**
   - the three tarballs and the zip;
   - both PKGBUILDs (`/usr/share/licenses/prikk/THIRD-PARTY-NOTICES`);
   - the release policy's own checks of what an archive contains, if it has them. Find them, do not assume.
5. **The reference** (`install.md` or wherever `LICENSE` is named) says that the notices ship beside it.
6. **CHANGELOG** `### Added`. The release notes say every archive now carries `THIRD-PARTY-NOTICES`.

## Part 5-fix, FIRST: `main` is red on Windows (30 min, stop at 60; report `0.57.0-item-5-fix-report.md`)

**CI on `b8a300f7`, run `42829516211`: the Windows mutation test suite FAILED.** Two tests,
`the_committed_notices_are_what_the_graph_produces` and `…every_linked_crate_and_the_right_platform_sets`:
"prikk 0.56.0 is linked into the prikk binary and its package ships no licence file". Every other job is green,
`policy` included.

**Cause (read by the architect):** `notices.rs:77` recognises a workspace crate by the spelling of `cargo tree`'s
line, `word.starts_with('(') && word.contains('/')`. On Windows the path prints as `(D:\a\…)`, so prikk's own crates
are taken for registry crates.

1. **Classify by identity, never by spelling.** A crate is the workspace's when `cargo metadata` says so: its
   package's `source` is `None`, or it is in `workspace_members`. Match on `(name, version)`. Read `cargo tree` only for
   the set of names linked per target.
2. **A test that would have caught it on Linux:** feed the parser a Windows-shaped `cargo tree` line
   (`prikk-cli v0.56.0 (D:\a\prikk\prikk\crates\prikk-cli)`). It must not be listed. Add a red control.
3. **Read the Windows job in CI** on the fix commit, and say so in the report. The cross-target clippy gates do not run
   tests.

3. **Tests:** the Windows installer test in CI and the Unix one assert both files are installed and then removed.
   Add red controls.

## Part 5c: install, then uninstall, leaves nothing behind (30 min, stop at 60; report `0.57.0-item-5c-installers-report.md`)

`mkdir -p "$licence_dir"` creates `~/share/licenses/prikk` for `--prefix ~/bin`, and the uninstaller removes only
`prikk/`. So `~/share/licenses` and `~/share` remain. The default leaves an empty `~/.local/share/licenses` where
there was none. `install.md`'s "nothing else to clean up" is then false.
1. **Test it as tree equality:** list the tree before the install and after the uninstall, and compare, for:
   - the default;
   - a `bin` prefix whose parent has `share/`;
   - `~/bin` (the parent has none);
   - a non-`bin` prefix.

   Add a red control.
2. **Choose the rule and state it in `install.md`:**
   - **(i)** beside `bin` only when `<parent>/share` already exists, else inside the named directory; the
     uninstaller looks in both places;
   - **(ii)** remove, when empty, every directory the installer could have created, never one that existed before.

   Say which, and why.
3. **Windows:** the same tree-equality assertion in Scenario A2.
