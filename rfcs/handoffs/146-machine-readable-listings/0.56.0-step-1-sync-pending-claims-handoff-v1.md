# 0.56.0 step 1 — `sync pending` maps each pending patch to its claims (two sittings)

**Live 2026-10-29, and it is next.** The owner decided on 2026-10-24 that planeter's request leads 0.56.0, and confirmed
the scope on 2026-10-29. **The request** (planeter, letter of 2026-10-21, §2) asked, per pending patch, for:
- its id;
- the claim id or ids it belongs to;
- the claim's signer outcome (sound, or unverifiable and why);
- the parent block id the claim names.

> That is exactly the mapping we cannot get today (claim → patches), and with it we could stop declaring patch lists
> ourselves.

**Today:** `sync pending` prints a count and the ids (`sync.rs:301`–`310`), and it has no `--format json`.

## Part 1a — `sync pending --format json`, and the help sentence (about 90 minutes)

1. **A new JSON document, `sync-pending-v1`**, from `sync pending --format json`. One entry per pending patch:
   - `patch_id`;
   - `claims[]`, each with:
     - `claim_id`;
     - `parent_block_id`;
     - `signature`: `{"outcome": "sound" | "unverifiable", "key_id": …}`, from `verify_claim_signature`
       (`recognition_claim.rs:143`) and its `ClaimSignatureVerification` (`:121`). Report it; never refuse on it.
   - **A patch no claim names** appears with `claims: []`. Say whether that can happen, and how.
   - **A patch named by two claims** appears once, with both claims.

   **The text output keeps its two lines unchanged,** since a script may read them.
2. **Order:** stable and documented, by patch id as today. `claims[]` is ordered by claim id.
3. **Cost:** `accepted_but_unsealed_patch_ids` already reads the patch ids, and the claims are enumerated once. **Do not
   read each claim's patches once per patch;** build the mapping in one pass. Say what it reads.
4. **The help sentence** (the owner's ruling F): `sync pending`'s `--help` line, and `commands.md`, say that pending means
   accepted into this repository's own queue and not yet sealed. Pending patches arrive only through `sync accept`;
   `archive import`'s received history is not pending. Check that sentence against the code before writing it.
5. **`commands.md` documents `sync-pending-v1`** field by field, with one example.
6. **Tests:**
   - one claim with two patches;
   - two claims sharing a patch;
   - an unverifiable signer (a key not adopted);
   - an empty queue (`"patches": []`);
   - the text output unchanged.
7. **Red:** drop the `claims` join, and the test fails.

## Part 1b — `state` in `show --format json`, and a pending edit's path (about 90 minutes; live after 1a is accepted)

1. **A `state` field in `show --format json`** for a patch: `queued`, `pending` or `sealed`.
   - **queued:** in this repository's own WAL;
   - **pending:** accepted and unsealed;
   - **sealed:** reached from a block.

   Define each from source, and say what a patch that is several at once reports. It is additive, so the schema version
   stays.
2. **`show <patch-id>` resolves a pending text edit's path through its claim** where the claim's parent block is sealed or
   received. Today the field is `"unresolved_node_id"`; renames and deletes already carry paths.
   - **Where the parent is itself pending** (a chain), leave it unresolved. That is step 2B's `extract` chain work.
   - **Name the reason** in the JSON. Never guess a path.
3. **Tests and a red control,** as in 1a. **Text:** `commands.md`, and the CHANGELOG.
