## Part LW: a wait must not refuse at its holder's release, on Windows (60 min, stop at 90). DONE (accepted 2026-11-28, `7ef218d8`)

**What is wrong.** The architect found it reading CI run `46106128987`, on commit `0554ef01`, a records-only push, 2026-11-28. It is in
the ROADMAP row "On Windows, a wait for a lock can refuse at the moment its holder releases it".
- **What failed:** the Windows mutation suite, 2,100 passed and 1 failed, `lock::wait_tests::a_body_still_being_written_is_read_again`.
- **What the trace showed:**
  - `IncompleteBody` twice;
  - then `SameProcess, 131 bytes` for 200 ms;
  - then the refusal `(waited 0.2 s: the holder could not be read)`.
- **The cause, from the code:** in `wait_decision` (`crates/prikk-store/src/lock.rs:760-765`), `read_file_if_exists` returning `Err`
  refuses at once. Only `Ok(None)` (released) retries.
  - On Linux an unlink removes the name at once.
  - **On Windows a file being deleted keeps its name for a moment and cannot be opened.** So the read fails during an ordinary release.
- **How often:** 1 of 6 Windows runs of this code that day. It shipped in 0.59.0. It fails closed, but its sentence names `prikk unlock`
  for a lock that is already gone.

1. **Confirm the cause or correct it.** Read what `read_file_if_exists` (`foundation/fsutil/anchored/read.rs`) returns on Windows for a
   file in that state. Cite the code or the platform documentation; do not guess an error code.
2. **The fix, recommended (say if you find better):** a read error while waiting is looked at again for the same moment an incomplete body
   gets (`INCOMPLETE_GRACE`, 250 ms, and the same test hook).
   - **A file then gone:** retry the create.
   - **A file then readable:** judge it as today.
   - **A file still unreadable after the grace:** refuse exactly as today, with the same suffix.
   - **One constant, not a second one,** unless you show the two moments differ.
3. **The tests:**
   - **a test hook makes the read fail, then the file disappears:** the wait takes the lock. **It must fail on every platform without the
     fix** (the red control: remove the grace);
   - **a read that keeps failing** refuses after the grace, with today's sentence;
   - the CI test that failed stays, unchanged.
4. **Every other reader of a lock file, for the same Windows state.** Classify each by what it does with an unreadable lock:
   - `unlock`'s listing (`unlock.rs`);
   - `refs/in_flight.rs`;
   - `foundation/layout.rs`;
   - and any other you find by grep.
   For each, say whether it reports a false state in that moment, and fix it in this part only if the fix is the same one. Otherwise list
   it with the case.
5. **The report:**
   - the cause, cited;
   - the change;
   - the tests and their red controls;
   - the readers' table;
   - the Windows CI result is read by the architect after the push.

## Part T: `tag create --target` names the tip after every wait (60 min, stop at 90)

**What is wrong.** External review 058 §2.5, on the 0.59.0 candidate; the ROADMAP row "`tag create --target <ref>` names the tip it read
before it waited".
- `tag.rs::run_create` resolves `--target` to a block id (`resolve_target_block`) before `create_local_tag`'s `ensure_may_publish`, where
  the 0.59.0 wait happens.
- **So a tag created after waiting for a publication in flight is written at the tip the ref had before it.** The reviewer measured
  `tags/late` at `c05f838f…` while `heads/main` was then at `b24e7db5…`.
- `branch create --from <ref>`, in the same shape, re-reads and lands on the published tip.
- **Also (§2.4, not new in 0.59.0):** beside a publication in flight, with the wait off, `tag create` succeeds at the old tip.

1. **Resolve the target after every wait,** as `branch create` does. If a snapshot rule is better for some command, state it in the
   command's help and its output. Either way, the tag's target is what the command printed it would be.
2. **Read the same order in `sync adopt-tag`, `merge --into` and `checkout --plan-only`'s resolvers.** Fix each one that resolves before
   its wait, or state why it may.
3. **The test is the reviewer's shape:** a publisher frozen with a publication in flight, a `tag create --target heads/main` that waits,
   then the publisher released.
   - **The tag names the tip the publisher published.** Red control: today's order.
   - Build it with the suite's own means. The reviewer's `probe29.sh` (`.git-exclude/upstream/external-architect/receive/058-reply-the-0-59-0-candidate-8af5c1db/reproduce/`)
     may be adapted under 057's terms, as K did, with its attribution.
   - Run it n times on tmpfs and give n/N against 0.59.0's old-tip result.
4. **The report:**
   - the order per command;
   - the change;
   - the test and its control;
   - the n/N.

## Part S1: `show <block>` derives from the nearest checkpoint (90 min, stop at 120)

**What is wrong.** The ROADMAP row "`show <block>` replays from the root".
- **Measured by the architect** on `main` with `~/.pgtmp/arch-tools/inkl-s2.sh`, 2,000 one-line edits on tmpfs:
  - 4–6 ms near the root;
  - 23–35 ms at height 1,001;
  - 57–64 ms at 2,000;
  - **at 1,001:** 6,082 block reads, 2,082 patch reads and 24,528 `openat`.
- **Cause:** `crates/prikk-store/src/show.rs` derives the parent's state with `lifecycle_state_at` (`:407`, `:980`) and walks
  `lineage_horizon` (`:290`, `:984`). Both walk to the root (`merge/evidence.rs:144`, `:182`).
- **`seal` already derives from the nearest authenticated snapshot:** `block_state::anchored_parent` (RFC 159).
- **We promised inklkunn this in 0.60.0** (our letter of 2026-11-25).

1. **Reuse seal's mechanism as it is:** `anchored_parent_state` and the anchor-trust function.
   - **Never a weaker admission for a reader.** Its own rule is *"Every doubt is `None`"*, and `None` runs today's full walk.
   - Say which of `show`'s three call sites this serves, and how.
2. **Equality is the acceptance test:**
   - for every block of the 2,000-block corpus, and for a merge and a rollback block, `show`'s output (text and JSON) **is
     byte-identical** derived from the checkpoint and derived from the root;
   - **red control:** perturb the anchored derivation (for example, an off-by-one anchor), and the test must fail.
3. **Measure, release build** (memory: a timing is a property of its build):
   - `show` at heights 1, 1,001 and 2,000, against 0.59.0, with block reads, patch reads and `openat` counted;
   - **say what share of the corpus's blocks takes the fallback,** and why.
4. **`show` on a received ref, or in a repository with no replay-verified record:** say what it costs now, and what the page says. The
   cost may stay; nothing may be made weaker.
5. **The report:**
   - the design;
   - the equality test and its control;
   - the table against 0.59.0;
   - the fallback share.
