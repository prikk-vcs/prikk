## T2 — `commands.md`'s `state` paragraph says the opposite of the code

The paragraph (`commands.md:168-180`) says a patch whose block no tip reaches reads `"sealed"`, "a bare-id read never
checks reachability". The code (1b2's R2, measured) gives `"pending"` by either id.
- **Say:**
  - `state` is the same whichever id names the patch;
  - a patch no tip reaches reads `"pending"`, the same membership `sync pending` lists, even while its block is still
    held.
- **Drop:** "genuinely" and "a real crash window".
- **One commit, docs only,** with `reference-check` and `git diff --check`.

## 2A — what a delivery may change, and what it leaves (items #4, #5, and the pending question)

**Sources:**
- planeter, `.git-exclude/upstream/planeter/receive/2026-10-21-what-we-measured-delivering-newer-history-to-a-keyless-forge.md`
  §1–§2;
- the owner's decision, 2026-10-29, *"Refuse by default"*: an older or diverged delivery is refused unless an explicit
  flag accepts it.

**1. Which commands, a rule over a class.** Every command that writes or moves a pointer, local or received, from
delivered input:
- `archive import` (`land_as_received_pointer`, `archive/import.rs:971`) and `archive import --adopt`;
- `bundle import`;
- every caller of `write_received_pointer` and `write_received_pointer_under_held_lock` (`received.rs:94`, `:132`);
- `sync accept`: say from source whether it moves any pointer at all. If it does not, say so with the evidence, and say
  what "older" could mean for it (for example, a claim whose patches some held history already sealed).

Grep for the writers; do not stop at the commands you know. Measure each on a build: today's outcome for a newer, an
equal, an older, a diverged and an unrelated delivery, into a pointer that exists, and into one that does not.

**2. The classes.**
- `bundle preview` already classifies against a local ref (`bundle.rs:310-340`): `no-local-history`,
  `does-not-connect`, `already-included`, `fast-forward`, `diverged`.
- **It has no class for a rollback.** "Already included" means nothing to do when previewing, but **replacing a pointer
  with an ancestor of its current tip moves it backward.**
- **Propose the classes** a delivery gets against the pointer it would replace (local or received), with one shared
  classifier for every command in §1, and the names that appear in JSON.
- **Say whether `preview` and the importers then share it,** so that a preview and an import of the same delivery can
  never classify differently.

**3. The refusal.**
- **Which classes refuse by default** (owner: older and diverged; propose what happens to an unrelated one).
- **The flag:** propose a name, with one alternative.
- **The `refusal-v1` id.**
- **Where in `bundle import`'s two passes the decision is made.** It must come **before the first object is written**.
  Say what pass 1 already knows (the delivered tip and its block graph) and what else the classification must read.
- **What a refused import leaves:** nothing, and say how a test proves it.

**4. `archive import --adopt` reports the classification (#5).** Today, with the local ref absent, `--adopt` publishes
whatever the archive's tip is, even when a received pointer of the same name holds a newer tip (planeter §1).
- **Say what it compares against** in that case.
- **Say what the JSON and text report.**

**5. What a delivery leaves: the `pending` question (review `0.56.0-step-1b-review-v1`, R2).**
- `sync pending` lists every Patch object no tip reaches. After `received remove`, the removed history's patches read
  "pending (accepted, unsealed)" with `"claims": []`, although `sync accept` never saw them. A refused `bundle import`
  that wrote Patch objects leaves the same state.
- **Nothing in the repository records an acceptance.**
- **Lay out the options,** at least these three:
  - **(i)** record an acceptance, which is a format change: say where, and what an older binary does with it;
  - **(ii)** define `pending` as a held patch no held Block names (cheaper, and it changes the listing again);
  - **(iii)** keep the membership and say it plainly.
- **Show each option against #9** (the owner: *"Count them, tell planeter"*: `verify`/`doctor` count an unreached Blob
  or Patch), so one object is never counted by two commands with two different meanings. Recommend one.

**6. The case table.** One row per command × class × pointer state (absent / local / received). Columns:
- outcome;
- exit code;
- `refusal-v1` id;
- what is written before the refusal;
- what `--format json` says;
- **what a script written for 0.55.0 sees.**

**7. Decisions for the owner,** each with options and a recommendation: the classes, the flag's name, unrelated
histories, the `pending` option.

## 2B — `extract` over a chain of pending claims (item #2)

**Sources:**
- planeter, `.git-exclude/upstream/planeter/receive/2026-10-27-extract-and-a-chain-of-pending-claims.md`;
- `prepare_extract_plan_for_claim` (`extract.rs:172`), which refuses `claim-parent-not-sealed` today;
- 1b's chain reason in `show`.

1. **The chain.** Claim C₂'s parent is the block that claim C₁ recognizes. C₁'s parent is sealed or received. Define
   the walk:
   - how C₁ is found from C₂'s parent id;
   - what happens when **two held claims recognize the same block** (refuse, or pick by a stated rule: say which and why);
   - a missing link;
   - a cycle;
   - a merge claim anywhere in the chain;
   - **a bound on the chain's length,** named with the reason.
2. **Trust.** For each claim in the chain, what its signature outcome must be (`sound`, `unverifiable`, `invalid`).
   - `extract` is a reader that writes files, so it never seals.
   - Say whether one `unverifiable` link is enough to refuse, or is only reported. **An `invalid` link always refuses.**
3. **Consistency of each link:**
   - the claim's patches fold onto the previous link's state;
   - path collisions, the same rule as today's claim path.
4. **The report.** `extract-report-v1` gains the chain (claim ids in order), additively. Say what
   `claim_parent_block_id` means for a chain.
5. **One resolver.** `show <patch>` should then resolve a chained pending edit through the same walk. **Say whether
   step 3 shares it, or leaves `show` with its chain reason.**
6. **Refusals** (`refusal-v1` ids), **the case table, and the decisions for the owner.**

## 2C — Unicode repository paths (item #11)

**Sources:**
- inklkunn, `.git-exclude/upstream/inklkunn/receive/2026-10-27-non-ascii-repository-paths.md`;
- the owner, 2026-10-28: design in 0.56.0, implementation in 0.57.0 or later.

1. **Today, measured:**
   - where a non-ASCII path is refused, by command and by layer (the path validator, the patch decoder, `extract`);
   - **what a binary of 0.55.0 or older does with a patch that carries such a path: the format question.**
2. **The format.** Whether this needs a new patch, object or repository format version, or only a capability marker.
   **Say what an older binary does with a repository and with a bundle or archive that contains one such path:**
   - a clean refusal naming the cause;
   - never a misread.
3. **Normalization.** NFC, NFD, or bytes as given.
   - What macOS (normalization-insensitive APFS), Windows and Linux each do when such a file is written and read back.
   - Propose the rule: store one form; refuse, or normalize, at the boundary; and **what `commit` does with a working
     file whose name is in the other form.**
4. **Collisions.** Today's ASCII case fold (`validate_no_path_collisions`) beside:
   - Unicode case folding;
   - canonical equivalence;
   - each platform's own rules.

   **Two paths that one platform cannot hold apart must collide everywhere,** or say why not.
5. **Limits:**
   - path length in bytes and in UTF-16 units (Windows);
   - reserved names;
   - characters to refuse anyway (controls, bidirectional overrides, and others, each with the reason).
6. **The release.** End with the release the implementation lands in, and its size in sittings, for the owner to
   decide.
7. **The case table** (platform × form × command), **and the decisions for the owner.**
