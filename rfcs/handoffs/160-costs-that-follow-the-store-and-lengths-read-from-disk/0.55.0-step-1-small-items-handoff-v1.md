## 1. `extract` refuses a destination inside the repository

**Why:** external review 035 §3.2, reproduced by the architect. The owner decided on 2026-10-24: the wording was fixed
in 0.54.0, and the refusal comes in 0.55.0. Today `extract` checks only that the target does not exist, so a path in
the worktree or under `.prikk/` is accepted. A copy in the worktree is then taken as content by the next
`commit --from-worktree`.

- **Refuse before anything is written** when the target, or its temporary sibling, resolves inside the repository's
  root (`.prikk/` included). Compare resolved paths by identity, never as text. Resolve the nearest existing ancestor,
  since the target itself does not exist yet. That also handles `..`, symlinked parents, and Windows case and
  short-name forms; say how each is covered.
- **A new `refusal-v1` id,** for example `destination-inside-repository`, and a message naming the repository root.
- **Tests:**
  - an absolute path inside the worktree, a relative path, a path under `.prikk/`, and a path reached through `..`
    from outside;
  - a symlinked parent that points inside (unix); on Windows, a case-different spelling of the repository root;
  - all refuse with nothing created, not even the sibling;
  - a path outside, including a sibling directory of the repository whose name starts with the repository's name
    (`repo-out` beside `repo`), succeeds.
- **Red:** remove the check, and those tests fail.
- **Text:**
  - remove the 0.54.0 caveat from `commands.md`'s `extract` entry, and say the command refuses;
  - the CHANGELOG entry (`### Output changes`);
  - the `--help` line, if it states the destination rule.
- **Smoke:** section 31 of `smoke-0.54.0.sh` copies into `smoke-0.55.0.sh` at release prep. List the new rows in the
  report.

## 2. `extract --claim` on a claim whose parent is not yet sealed

**Why:** review 035 §3.3. Today that case refuses with `"refusal": "damaged-repository"`, but the repository is not
damaged.

- **A new id,** for example `claim-parent-not-sealed`, and a message naming the claim and its declared parent. It says
  to seal or receive the parent first.
- **Find where the `missing Block` error comes from** on this path, and classify that case only. A genuinely missing
  object in any other position stays `damaged-repository`. Show both in tests: the unsealed parent gets the new id,
  and a deleted stored block still gets `damaged-repository`.
- **Red:** with the classification removed, the new test reports `damaged-repository`.
- **Smoke section 35** pinned `damaged-repository` through this very shape. Name that row in the report; release prep
  updates it.
- **Text:** `commands.md`'s list of refusal ids, and the CHANGELOG (`### Output changes`).

## 5. The Windows uninstaller and the installer job's timeout

**Why:** Part 6a4 review, recorded then.

- **Today:** when the user had no `Path` value at all, uninstall leaves an empty `Path` value that did not exist
  before.
  - **The fix:** the installer records in its marker that it created the value. The uninstaller deletes the value
    only when the marker says so **and** the value is empty after removing our entry. Any other value stays.
- **Control 5's "Shape B"** (no `Path` value) in `scripts/windows-installer-test.ps1` changes:
  - after uninstall, the value is **absent**, where it used to be asserted present and empty;
  - **red:** without the fix, Shape B fails;
  - a Shape D: the user adds another entry between install and uninstall, so the value is kept, holding only that
    entry.
- **Old markers:** a marker written by 0.54.x has no such field. The uninstaller must treat a missing field as "did
  not create", the old behaviour, and a test shows it.
- **The `windows-installer` CI job's `timeout-minutes: 45`** (`ci.yml:342`): its last five green runs took 5 to
  7.5 minutes. Set it to 20, with a comment citing those runs.
- **CHANGELOG:** `### Fixed`, one line.
- **The architect reads the Windows installer job** on the first CI run after the push.
