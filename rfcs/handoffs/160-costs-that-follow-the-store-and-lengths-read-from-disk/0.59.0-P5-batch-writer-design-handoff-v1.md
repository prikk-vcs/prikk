## P5a: the batch's memory (90 min, stop at 120). DONE (accepted 2026-11-25, `.git-exclude/reviewed/0.59.0-P5-part-a-review-v1.md`)

1. **S1, the retained checkpoint states (a released defect; `### Security` when removed).**
   - **Where:** `BatchFold::fold` clones the whole state at every checkpoint (`block_state/batch_fold.rs:111-112`). `SealBatchPlan::fold`
     keeps every clone until the loop reaches its block (`seal_from_accepted/batch.rs:425-439`, drained by `take_step_for`).
   - **The size:** in a tree that grows a path per claim it is about 0.81 × claims² bytes. M1 measured 20 MB at 5,000; the architect's
     out-of-sample check is 15.9 and 16.7 MiB at 2,000.
   - **Design how the fold holds one state at a time:**
     - **(i)** the loop re-derives a checkpoint's state when it reaches it (at most 64 claims' patches onto the running state); or
     - **(ii)** a second running fold advances with the loop and writes each snapshot from its own state; or
     - **(iii)** anything better.
   - **For each:**
     - the time it costs, measured or bounded;
     - what it reads;
     - that the bytes sealed are identical (the snapshot's entries and texts);
     - and **the case table's crash row:** a kill mid-batch must leave what K's `sync seal` sweep accepts today, so the sweep must stay X 0
       unchanged.
   - **The target:** the growing shape becomes linear. Say the predicted per-claim slope.
2. **S2/S3, the object index held 3.9× its one-copy size: count first.**
   - **The measurement:** live allocations per stack (the one-line probe change M1 named), at fixed 10,000.
   - **Then say which it is:**
     - capacity slack from an amortised `extend`;
     - copy-on-write copies kept alive by older snapshots (`index_snapshot.rs:171`, `release_kept` at `:286`);
     - or both.
   - **The answer:** (a) needed, with its bound per stored object; or (b) not needed, and what dropping it changes.
3. **S4/S5, every accepted claim in the repository, read to seal one batch** (`enumerate_stored_claims`, the claims index):
   - **The question:** can the order-ambiguity check (`refuse_if_order_ambiguous_indexed`) and the parent check
     (`require_parents_reached`) read only the claims that name the batch's blocks or patches?
   - **Answer it with the check's own argument,** not by assumption: what a claim outside that set could change in the decision.
4. **S8, the decoded envelope of every ref-log record** (about 1.4 KB per sealed block, ten sites): which of it the publication
   precondition needs (`ensure_publication_precondition_with_replay`, `refs.rs:276`), and what the rest is.
5. **CPU:**
   - **The cost:** each claim's state root is computed over every path (`entries_from_state`, `compute_state_root` per claim), so claims ×
     paths in time as well. The growing 10,000 run took 274 s against 63 s fixed.
   - **The options:**
     - an incremental root (which leaf changed, and the path to the root); or
     - an argument, with numbers, that the cost is acceptable where it matters (the 256 MiB artifact's 360,000 claims).
   - **Time cost matters,** so say which, with the measured slope.
6. **The docs sentences** for what the batch genuinely needs: from M1, about 125 B per stored object for the index and about 0.6 KB per
   accepted claim. They are written at P5's close, **with the numbers P5 leaves**. Here, say what they will be under each option.
7. **Stop at P5a's report.** The architect rules each item: build, do not build, or a question for P5b.

## P5a1: the fold holds one state at a time, and the claim drops its read snapshot first (90 min, stop at 120). LIVE

**A released, peer-driven defect: `### Security`.**
- **The cause:** in a tree that gains a path per claim, 0.58.0's fold kept every checkpoint's whole state, about 0.81 × claims² bytes
  (M1, P5a).
- **The architect's check:** your prototype gave 27.6 → 24.5 MiB at 3,000 claims, with byte-identical containers, and a control that
  moved the hash.

1. **S1, option (iii):**
   - The loop advances a second running fold, and writes each checkpoint's snapshot from that fold's own state.
   - **The up-front pass is apply-only** (`apply_candidate_patches`, no entries, no root). It runs **only when the target branch is the
     current one,** since its only product is the final state the in-the-way check reads.
   - **Fail-safe as today:** a running-fold error at a claim seals it, and every later claim, from disk.
   - **No `P5A_*` switch, timer or probe survives into the build.**
2. **S2, the scoping fix:** `read_snapshot` and `fresh` are dropped (or scoped) before `ObjectWriteSession::open`
   (`seal_from_accepted.rs:211`, `:214`, `:436`), so a write's `Arc::make_mut` no longer copies the whole index.
3. **The steps buffer:** no capacity kept after the pops (`shrink_to_fit`, or a `Vec` read by index).
4. **Proof that the plan is used:** a counter (test-visible) of the claims sealed from the plan against those sealed from disk. A normal
   batch asserts **zero from disk**, in both shapes.
5. **Tests:**
   - **byte-identity:** the containers after a growing batch and after a fixed one equal today's, on the current branch **and on
     another branch** (the path the prototype did not run). Built from one base, sealed with the old code and the new;
   - **a control** that drops a snapshot entry, and must make the identity fail;
   - **memory:** a test-visible assertion that the fold holds at most one checkpoint state at a time, not a timing;
   - **the real-kill sweeps:**
     - `sync_seal_batch` stays X 0, unchanged;
     - **new, `sync_seal_checkpoint`:** a base of 62 sealed blocks, then a batch of 3 claims, so the batch crosses a checkpoint. X 0 on
       today's code first, then on the build. **Not** the 66-claim, 3,106-ordinal shape, which costs minutes on CI.
   - Red controls: the old retention back; the snapshot kept across the write session.
6. **Measured on the final build,** with planeter's `sealmem.sh grow` at 1,000, 3,000 and 5,000 claims, and the fixed shape at 10,000:
   VmData and CPU against today. **The growing slope should be linear.** Say the measured per-claim slope, and whether 10,000 was run.
7. **CHANGELOG:**
   - **`### Security`:** the curve measured at 1,000 to 10,000, and the extrapolation labelled.
   - **The reach:** a forge sealing a peer's batch in a tree that gains paths.
   - **The way round in earlier versions:** none measured beyond one point. Say so.
8. **The rules as in step 0:**
   - 15 gates;
   - a final build from the committed tree into a fresh target directory;
   - stage by path;
   - the ten output constraints (no output should move: say so, measured).
