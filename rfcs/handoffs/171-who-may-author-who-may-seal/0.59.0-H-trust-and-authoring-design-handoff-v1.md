## H1: what is true today, measured (nothing designed). DONE (accepted 2026-11-26; `.git-exclude/reviewed/0.59.0-H-part-1-review-v1.md`)

1. **Key custody:**
   - where `setup` puts each seed, and what each command reads (author, maintainer, both, neither), for every command that signs or
     verifies. **This is a table from the code, and each row is checked on the binary.**
   - **Can an author-only setup exist today?** Set one up (no maintainer seed anywhere prikk looks) and run every command an author needs.
     **Say which refuse, and with what.**
2. **Delivering an author's work:**
   - today only a sealed block under the author repository's own key, which the receiver re-seals;
   - **measure `sync build` → `sync accept` → `sync seal` with the author holding no maintainer seed;**
   - **is a queue of unsealed patches deliverable?** Say what exists, and where it stops.
3. **Trust transitions:**
   - **what `trust maintainer add` and `remove` write** (signed or not, by whom);
   - **what a copy can check** (does `verify` on a copy see that a key was added by an adopted maintainer?);
   - **what removal does to history** (planeter's measurement, reproduced).
4. **Least privilege, command by command:**
   - which commands need a seed only to plan (`ref complete --plan-only`, the repair verbs' `--plan-only`, `doctor`), and why;
   - **a plan that signs nothing should need no seed.** Where it does, find out why.
5. **The report:** the tables, each fact with the command that showed it. **No design.**

## H2: authoring and delivery, designed (90 min, stop at 120). DONE (ruled 2026-11-26; `.git-exclude/reviewed/0.59.0-H-part-2-review-v1.md`: route 1 is the proposal path; route 3 refused, measured; items 3 and 5 accepted with changes; item 1 re-asked in H2b)

**Start from H1's report and its review** (`.git-exclude/reviewed/0.59.0-H-part-1-review-v1.md`).

**For each item:**
- lay out the options;
- recommend one;
- price it in code, tests, docs and output changes;
- say what a refusal would name.

**The architect rules. Nothing is built: builds are 0.60.0 at the earliest.**
- **Measure where an item says so.** Test keys only, in a temporary `HOME`.
- **Less is more:** an existing mechanism that suffices beats a new one, and "change nothing" is an option for every item.

1. **The author's machine, made on purpose.**
   - **Today** one exists only by `key generate --out <cfg>/author.seed` alone, or by deleting the maintainer files. Nothing makes one,
     and `key status` reports the maintainer seed as `missing`.
   - **Design:**
     - how one is made (a `setup` option, a `key generate` role, or the docs alone);
     - **what `key status` says there:** a declared author-only state, or `missing` as now;
     - **what `status`, `doctor` and `verify` say there.** No unactionable warning: a machine meant to hold no maintainer seed must not be
       told it lacks one. **Measure whether any command warns today.**
   - **Its refusals:**
     - `seal` and `sync build` advise "Create one with `prikk key generate`", the opposite of the machine's purpose;
     - `branch create`, `tag create` and `bundle export` say `ref heads/main does not exist in this repository`.
     **Write one sentence per refusal that names what works there,** and say how a command can tell an author-only machine from a
     maintainer that has lost its seed (or that it cannot).
2. **Delivery: what the author hands over, and what the receiver does with it.**
   - **Measure first: H1 measured delivery only with the sender's key already adopted by the receiver.** The acks' path (041, 043) is
     different: the author repository seals under a **repository-local maintainer key that the receiver has not adopted**, and the
     receiver reviews and re-seals under its own key.
   - **Run both routes with that key not adopted:**
     - `sync build` → `sync accept` → `sync pending` → `sync seal --claims`;
     - `bundle export` → `bundle preview` → `bundle import`, with and without `--adopt`.
     For each: what lands, what `verify` says on the receiver, and **whether the receiver's sealed history carries the author's patches
     with their author signatures intact.**
   - **Ack 041's two conditions:** the authoring process can neither read the receiving maintainer's seed nor write the receiving
     repository.
     - For each step, say which machine runs it and which seed it reads.
     - Say whether either condition fails anywhere.
   - **Then design:** whether that path suffices, or what is missing.
     - **A new object for unsealed work is the last option.** Price it against the existing path.
     - The queue in the author's WAL (H1 §2) stays undeliverable unless you show a case the sealed path cannot serve.
3. **Per-task author keys.**
   - **Say how a task gets its own author key,** and what the receiver sees of it: today "continuity only, not a trust decision".
     The tools are `key generate`, `PRIKK_AUTHOR_SEED_FILE` and `PRIKK_AUTHOR_KEY_ID`.
   - **Say whether the key ids stay distinct** (key-id first, K6), and what `log` and `show` name.
   - **Flag, do not design:** whether anything should bind a task key to a person. That is an owner question.
4. **What the receiving maintainer reviews before sealing.**
   - **On the route from item 2:** can the receiver see each patch, its author key and what it changes before it signs?
   - **Name the commands that show it** (`sync pending`, `bundle preview`, `show`, `diff`), and the gap if there is one.
5. **Least privilege: `ref complete --plan-only` without the seed** (inklkunn's ask 1).
   - The plan reads the seed only to print `completing key: <id>` (H1 §4). `key_material::configured_key_id_without_the_seed` already
     serves `bundle preview --adopt`.
   - **Design what the plan prints when the configured key id has no seed.** The plan must still say what the real run will need, as
     `bundle preview`'s note does.
   - The real run still proves the seed.
6. **The report:** `.git-exclude/review-request/0.59.0-H-part-2-report.md`. For each item:
   - the measurements, each with its kept output;
   - the options and the recommendation;
   - the tests a build would need;
   - the docs and the `### Output changes` it would bring.
   **No commit.**

## H2b: the author's machine under route 1 (60 min, stop at 90). DONE (ruled 2026-11-27; `.git-exclude/reviewed/0.59.0-H-part-2b-review-v1.md`: items 1, 2, 5 as recommended; items 3, 4 with the rule "every sentence true in every state it is shown in"; the missing-directory defect fixed in H2c)

## H2c: `setup --*-seed-out` into a missing directory refuses before `init` (30 min, stop at 60). LIVE, FIRST. A fix, committed, in 0.59.0

**The defect** (H2b §1, reproduced in the H2b review, D1):
- `setup <repo> --author-seed-out <dir>/a.seed --maintainer-seed-out <dir>/m.seed`, with `<dir>` missing, prints `initialized Prikk
  repository at …`, then fails (`failed to create <dir>/a.seed.key-id: No such file or directory`).
- **It leaves a `.prikk` with no maintainer key adopted.** A rerun finishes it (K6), so nothing is lost. **But a released command starts
  what it cannot finish,** against RFC 148 §2c and the rule that every refusal in a write sequence comes before the first write.

1. **`setup` checks, before `init` writes anything,** that the parent of each `--author-seed-out` and `--maintainer-seed-out` path exists
   and is a directory.
   - **If not, refuse with exit 1 and nothing written,** naming the directory and something typeable that works (e.g. `create it first:
     mkdir -p <dir>`).
   - **Do not create the directory:** where a secret lives, and with what mode, is the user's choice.
2. **`key generate --out <path>` into a missing directory** already fails with nothing written, but its sentence names `<path>.key-id`
   instead of the path given. **Same check, same sentence shape,** before anything is written.
3. **Tests:**
   - for each flag, and for both together: a missing parent, and a parent that is a file. **Exit 1, the sentence, no `.prikk` left, no
     file written;**
   - the `key generate` case;
   - **today's success cases unchanged.**
   - **Red control:** the check removed. The no-`.prikk`-left assertion goes red.
4. **`CHANGELOG.md`:** a `### Fixed` entry (the flags shipped before 0.59.0), and the sentence in `### Output changes`. **Docs:**
   `troubleshooting.md` or `key.md`, wherever `setup`'s seed-out flags are described.
5. **The 15 gates, a final build from the committed tree into a fresh target directory** (both hashes). **One commit.** Report:
   `.git-exclude/review-request/0.59.0-H-part-2c-report.md`.

## H3a: trust transitions, removal and rotation, designed; every consumer case answered (90 min, stop at 120). After H2c

**Nothing built:** builds are 0.60.0 at the earliest, after the owner reads the round.
- **For each item:** the options, a recommendation, the price (code, tests, docs, `### Output changes`, format changes), and what each
  refusal names.
- **Measure first where an item says so.** Test keys only.
- **Two fixed rules:**
  - **no state that no command clears:** prikk never freezes a repository whose every seed is lost;
  - **no claim wider than the mechanism:** a copy checks only what it carries.

**Inputs:**
- the ROADMAP row "Maintainer key rotation that keeps history verifiable" (planeter's three measurements, inklkunn's four cases, stikk
  023);
- external acks 041 and 043;
- H1 §3 (trust transitions are unsigned and keyless; removal fails `verify` for everything the key sealed; re-adding restores it);
- **the H2 review's "Two things for H3".**

1. **Signed trust transitions.** Today `trust maintainer add` and `remove` are unsigned and need no key (H1 §3), and a copy cannot tell
   who adopted a key.
   - **The options, at least:**
     - (a) unchanged, documented;
     - (b) a transition signed by an already-adopted maintainer key, recorded so a copy can check the chain from the first key;
     - (c) (b) plus a recorded way in when every seed is lost (planeter's measurement 2: today an operator adopts a new key with no
       signature asked, and `verify` exits 0).
   - **For each:**
     - what a copy checks;
     - what happens to a repository whose every seed is lost (it must not freeze);
     - **whether it closes route 3's laundering** (the H2 review's table: the copy's policy adopted K_x, which the author wrote);
     - the format change and how existing repositories, whose policies are unsigned, are read.
2. **Removal and rotation that keep history verifying.**
   - **Measure first:** map H1's three `PRIKK-TRUST-PUBLICATION-UNTRUSTED` findings per sealed generation to their objects.
   - **Design:**
     - **a recorded point:** a key retired from a point on, whose signatures before the point keep verifying;
     - **rotation:** a successor key, and whether the old key signs the hand-over;
     - **`trust maintainer remove --plan-only`** (stikk 023): it names what a removal would make fail;
     - **planeter's measurement 3:** `verify` judging received history (`remotes/`) under unadopted keys. Should it?
   - **The answer to the H2 review's second input:** whether a recognition claim, or `sync accept`, names a block's original sealer.
3. **Every consumer case, answered,** each with which option serves it, what it costs, and what stays impossible:
   - **inklkunn (2026-11-25 §3):** rotation without keeping the old key adopted; a lost key as a recorded state; a stolen key (from a
     point on its signatures do not count, and what it sealed before still verifies); permanent removal of content by re-creating a
     repository re-signed under the wiki's key;
   - **planeter (2026-11-21):** their measurements 1 to 3, and what their RFC 013 waits on.
4. **Flags for the owner, not designed:**
   - whether a task key is bound to a person (H2 §3);
   - whether prikk should ever let a repository be frozen deliberately (a policy that no unsigned operator can change).
5. **The report:** `.git-exclude/review-request/0.59.0-H-part-3a-report.md`. **No commit.**
