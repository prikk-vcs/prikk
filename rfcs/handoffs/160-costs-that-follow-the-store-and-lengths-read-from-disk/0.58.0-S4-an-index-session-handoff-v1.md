# 0.58.0 S4 — a writer reads the object index once per hold, not once per lookup

**Live 2026-11-15, and it is next** (S3 accepted: `.git-exclude/reviewed/0.58.0-S3-review-v1.md`).

**The owner ruled it in on 2026-11-15** (*"Both your recommendations are accepted."*), as **shared code**. Every writer
that appends objects meets it, and the ruling is to re-measure each one. S's five conditions bind it
(`.git-exclude/scratch/0.58.0-design-items-philosophy-check-v1.md`, section S).

**Two parts, one sitting each:**
- **S4a:** measure, and design. Ask before building if the options differ in a way the rule does not settle.
- **S4b:** build.

One report per part: `.git-exclude/review-request/0.58.0-S4-part-<a|b>-report.md`. The working rule is P2's.

## What it removes

**S3's baseline:** planeter's shape at 1,000 claims, with the loop alone. `containers/index.container` is read for
**1,826 MB, 58.6% of `sync seal`'s remaining reads.** S1 places it in two kinds of reads:
- the object index replayed whole on every snapshot open;
- the object index replayed on every object write under the lock (`resolve_object_location_locked`).

At 1,000 claims that is 10,780 reads.

## The rule

1. **One mechanism, the P2a pattern.** A decoded index is kept for the length of a hold, on the same `MutationRoot`, and is
   registered and released the way the held directories are. The writer's own appends update it in memory. Outside a hold,
   nothing is kept, and readers behave exactly as today.
2. **It must never be stale. This is the first condition, and it comes from S3's review.** `sync build` appends claims, and
   so index entries, under the object-store lock only, with no active lock. Another process can append to the index
   between two of this command's object-store lock acquisitions. Because the hold spans those releases, a kept index can
   fall behind the file.
   - **The expected shape:** at each object-store lock acquisition, compare the index file's identity and length (device,
     inode and size; the index is append-only) with what the kept copy decoded, and decode only the appended tail.
     A replaced file (a different inode) means a full re-read.
   - **Say what else can rewrite the index** (`doctor --repair-index`, compaction if any), under which lock, and show it is
     covered.
   - **A test:** another writer appends between two of this command's lookups, and the lookup sees the new entry.
3. **The damaged-index rule is unchanged** (rule 1 in `durability-recovery.md`: readers rescan the containers when the index
   is damaged). A kept index that finds a damaged tail does what a fresh replay does today.
   - The test that the S0/P2a review redefined
     (`a_damaged_index_entry_is_reported_by_the_replay_and_production_still_finds_the_object`) still holds.
   - **A new test:** damage appears in the tail between two lookups.
4. **Memory:** the decoded index is O(objects). State its size per object, and its peak at 1,000 claims and at the 100 MiB
   shape, against today's per-replay peak. It must not raise any writer's peak beyond what one replay already costs.

**Rulings on S4a (2026-11-15, `.git-exclude/review-request/0.58.0-S4-part-a-report.md`). S4b builds S4a's §3 design as written,
with these:**
1. **W1. The mechanism is Linux and macOS only,** with the held directories' `cfg`, and its tests carry that `cfg`. On Windows,
   `keep` stores nothing and every open decodes in full, as today.
   - **Why not W2:** an mtime is a weaker identity than (device, inode), and the rule is "never stale". One platform with a
     weaker staleness rule is a claim wider than its mechanism.
   - **Windows is not left without a way:** a file identity through `prikk-ffi` (`GetFileInformationByHandle`: the volume serial
     number and the file index) would give Windows the same rule. It is a ROADMAP candidate, not S4's: it adds FFI surface.
2. **`FileObjectStore`'s `lookup_cache` is left out.** It accounts for 0 of the 1,008 decodes. One user of the kept index,
   `IndexSnapshot::open`, is enough.
3. **The `Arc` with `make_mut`,** not a copy on each open.
4. **The canary's residual is accepted as stated.** It needs a second writer to rebuild the prefix and re-create our last
   record byte for byte at its offset, which the append protocol does not produce. Put the residual in the code's comment,
   word for word as the report has it.
5. **The equal-length rebuild that today's `ensure_current` misses** (it compares length only) gets its test, as S4a proposes.
   **Say in the report whether it is a released defect.** Can a real command produce an equal-length permuted index while a
   session is open? If one can, it gets a `### Fixed` entry with the measurement.
6. **S4a's corrected attribution goes in the report's numbers:** all 4 decodes per claim are `IndexSnapshot::open`. The
   predicted ~1 KB per claim is S4b's closing target.
