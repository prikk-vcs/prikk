## 2A — `bundle import` streams per object (first sitting, about 90 minutes)

**Today, measured by the architect on 0.54** (one random file per bundle, a fresh receiver, peak RSS through
`rusage_child.py`):

| bundle | peak memory | ratio |
|---|---|---|
| 16 MiB | 101 MiB | 6.34× |
| 64 MiB | 388 MiB | 6.07× |
| 200 MiB | 1,204 MiB | 6.02× |

**Answer from source:**
1. **Where the memory goes.** Trace `import_bundle` (`bundle.rs:895`) from opening the file to the last write. Name each
   point that holds the bundle's content (or a copy of it) in memory, and roughly how many copies coexist at the
   peak. Measure it with your own instrument, not this table alone, and also on a bundle of many small objects
   (for example 10,000 × 4 KiB).
2. **What must still hold.** List every guarantee `bundle import` gives today, with the test that pins each one. At
   least:
   - **refuse before writing** (`bundle_import_refuses_before_writing`): a bundle that fails validation writes
     nothing;
   - signature admission (`admit_carried_signatures`);
   - dependency order (`objects_in_dependency_order`);
   - the object-size bound;
   - the received pointer written last;
   - RFC 164 Rule D.
3. **The central question: streaming against "refuse before writing".** Validating the whole bundle before the first
   write is what forces reading all of it first. Lay out the options, for example:
   - **(a) two passes over the file,** validating while streaming and holding only ids and small metadata, then writing
     while streaming again. The file is read twice; memory follows the largest object;
   - **(b) staged writes, as `archive import` does** (`archive/import.rs`, with its interrupted-import record and
     `cancel_import`): stream into a staging area, publish only when everything validates, and recover or cancel after
     a crash;
   - **(c) anything better you find.**

   For each option give: peak memory (and what it follows), bytes read, what a refused bundle leaves on disk, and the
   crash behaviour.
4. **For the option you recommend, the case table** (`prikk-recovery-rule-needs-a-case-table`): crash at each write
   point × what is on disk × what `verify` and `doctor` say × what a re-run of the same import does × what a different
   import does next. Cover both outcomes: a bundle that validates, and one that does not.
5. **Untrusted input.** A bundle is untrusted. Say how the recommended design keeps every bound and refusal working
   when objects arrive in a hostile order, with lying lengths, or with an object over the bound late in the file. Name
   the existing tests that must keep passing, and the new ones you would add.
6. **The target, stated as a measurable sentence.** For example: "peak memory follows the largest object plus
   O(number of objects × small constant), not the bundle". Name the instrument and sizes that will prove it.

## 2B and 2C — F2 and AUD-01 (second sitting, about 90 minutes)

### 2B — listing by type reads the whole container (F2)

From RFC 160's inventory: *"listing by type reads the whole container, on `sync seal`'s path too."*
1. **Find every caller** of listing objects by type, and which commands reach it (`sync seal` included). Measure the
   bytes read by one such command at three store sizes.
2. **Options:** through the object index, which already knows each entry's type? A per-type offset list? Something
   else? For each, give the cost, the format change (if any: a format change is a much larger decision), and the
   crash behaviour.
3. **Recommend one,** with the target as a measurable sentence.

### 2C — the object index is held whole and searched linearly (AUD-01)

From ROADMAP's audit table: `IndexSnapshot::lookup` (`object_store.rs:472`) is a linear scan, so `verify` and `seal` do
O(objects) per lookup. RFC 133 §6d.2 requires the fix to be measured for **memory as well as time**: a map can make
lookups fast while enlarging the structure.
1. **Measure today:** lookup time and the index's resident size at 100, 10,000 and 100,000 objects. Use RFC 133 §6d's
   growth series as the reference (about 133 bytes per node).
2. **Options, at least:**
   - a hash map built when the index opens;
   - **a sorted vector with binary search,** which keeps the same memory and gives O(log n);
   - leaving it, if the measured cost does not matter at realistic sizes.

   Each keeps "the last entry wins". Show how.
3. **Recommend one,** with both measurements as the target.
