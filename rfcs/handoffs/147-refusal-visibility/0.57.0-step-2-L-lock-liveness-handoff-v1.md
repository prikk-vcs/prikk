## What is true today (read by the architect, 2026-11-08)

- **The lock body** (`lock.rs:395`) is `pid=<n>`, `kind=<kind>`, and `note=PR-007 lock has no stale-lock stealing yet`.
- **Liveness** (`unlock.rs:75–108`):
  - on Linux and macOS, `kill(pid, 0)`: `Ok`/`EPERM` → appears running, `ESRCH` → does not, other errors → unknown;
  - **on Windows, `prikk_ffi::process_liveness` (DC-99)**, with the same three answers;
  - elsewhere, unknown.
- **`unlock --lock <path>`** clears whatever the answer is, with `--yes` or `--force` as synonyms (`cli/src/unlock.rs:29`).
- **The body's only reader is `unlock.rs::parse_lock_body`** (also at the 0.56.0 tag). It keeps `pid=` and `kind=` and
  ignores every other line, so an older binary should list a new body unchanged. Measure this; do not assume it.
- **Step 0c's racy-entry horizon is the active lock file's creation stamp, not its body.** A longer body must not
  change when or how the file is created. Keep `create_lock_file`'s one exclusive create and its one write. The file
  is visible before its body is complete, today as well, so an `unlock` that reads an empty or partial body must
  answer "unknown", never "does not appear running"; add a test for it. Read the holder's own fields once per process,
  not on every lock taken.
- **Two sentences are stale:**
  - `concurrency-locking.md` says the check runs on Linux and macOS and is "unknown on other platforms", but Windows
    has one;
  - `prikk-store/src/unlock.rs:30` calls a positive result "reliable evidence to refuse".

## Part L1: a lock names its holder, not just a pid (90 min, stop at 180)

1. **First, a case table, before any code.** For each platform you can run (Linux here; macOS and Windows through CI
   tests), say what the holder record can be, and what each liveness answer will be, for:
   - the holder alive and the same process;
   - the holder dead;
   - the pid reused by another process (a different start time);
   - the holder in another PID namespace;
   - the machine rebooted since the lock was taken;
   - a lock body written by 0.56.0 or earlier, which has no new fields.
2. **What to record,** beside `pid` and `kind`:
   - the holder's **start time**: Linux `/proc/self/stat` field 22, macOS through `prikk-ffi`, Windows
     `GetProcessTimes` through `prikk-ffi`;
   - on Linux, **the PID namespace** (`/proc/self/ns/pid`) and **the boot id** (`/proc/sys/kernel/random/boot_id`);
     a start time counted since boot repeats across reboots;
   - on macOS, the boot time.

   **Every new OS call goes in `prikk-ffi`; `prikk-store` gains no `unsafe`.**
3. **The answers:**
   - **appears running** only when the pid is alive, its start time equals the recorded one, and (Linux) the boot id
     and namespace match;
   - **does not appear running** when the pid is gone, its start time differs (reuse), or the boot id differs
     (rebooted);
   - **unknown** when the recorded namespace is not ours, a field cannot be read, or the body is from an older prikk;
     the listing says which.
4. **Compatibility, measured both ways:**
   - 0.56.0's `unlock` reads a new lock body: it must ignore the new lines and still list the lock (check
     `parse_lock_body` at the tag, and run the published 0.56.0 binary against a new body);
   - the new `unlock` reads an old body: the answer is "unknown", saying "written by an older prikk".
   - **A partial new body must not read as an old one.** A new body is written while its file is already visible, so a
     reader can catch it truncated: `pid=12` of `pid=1234`, or the pid without the start time. So the body needs
     something that tells "complete and new" from "old" and from "partial", such as a version line first and an end
     line last. Choose the shape and say why. A partial body answers "unknown", saying "still being written, or
     damaged", and never uses its pid.
5. **Tests** for each row of the case table that can be built on the running platform (namespace and reboot by
   writing the body by hand), and a red control per answer.
6. **Docs:**
   - `concurrency-locking.md` defines the three words once, in one place, and lists what each platform records;
   - correct the Windows sentence;
   - correct `unlock.rs:30`'s "reliable evidence to refuse" to what L1 makes true.

## Part L2: the refusal (60 min, stop at 120)

1. **`prikk unlock --lock <path>` refuses a holder that appears running,** unless `--force`. It exits 1 with a
   precondition naming the pid, the start time, and that `--force` clears it anyway, at the risk of corrupting what
   that process is writing.
   - `--yes` keeps its meaning for "does not appear running" and "unknown". `--yes` and `--force` stop being synonyms.
   - The interactive prompt says the same.
2. **The two words appear once,** in the help line and `concurrency-locking.md`, and the error points there.
3. **The release notes (CHANGELOG `### Upgrading`)** name the change for scripts that pass `--yes` or `--force`
   against a live holder.
4. **Tests through the binary:**
   - a live holder (a child process holding the lock): `--yes` refuses, `--force` clears;
   - a dead holder: `--yes` clears;
   - an old body: `--yes` clears.

   Add red controls.
5. **The ROADMAP's lock-liveness row and the 0.57.0 row's wording** are the architect's to close afterwards.
