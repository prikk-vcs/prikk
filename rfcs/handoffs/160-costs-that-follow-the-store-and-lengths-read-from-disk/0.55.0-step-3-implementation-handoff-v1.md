## Part 1 — 2C: an id lookup that does not scan (about 90 minutes)

**Why:** `verify` and `bundle import` grow quadratically.
- **Measured on tmpfs:** `verify` takes 0.034 s at 1,000 objects, 0.31 s at 10,000 and 1.35 s at 30,000. That is
  about one full index scan per object.
- **Extrapolated:** about 9 s at 100,000 objects.

**1. Enumerate every linear id search over index entries first.** The 2B/2C report named one; the architect found
five:
- `object_store.rs:476`, `IndexSnapshot::lookup`;
- `object_store.rs:120` and `:128`, `resolve_cached` over the `LookupCache`;
- `object_store.rs:330`, `resolve_object_location_locked`, which also re-reads the whole index file on every call;
- `foundation/index.rs:502`, `lookup_object_location`.

For each, say:
- who calls it, and whether a command reaches it once per object;
- every path that changes its entries: the snapshot's `open` (`:455`, `:461`, `:466`), `ensure_current_impl`'s replace
  and `extend`, and `LookupCache`'s build.

**2. The change (C1):** keep each `Vec<IndexEntry>` as it is, and add a `HashMap<ObjectId, u32>` from id to position.
- **Updated on every path that changes the vector:** inserting in order, `extend` inserting the new tail, and a
  replace or rebuild rebuilding the map.
- **Converting a position to `u32`** is checked, never `as`.
- **Do it for `IndexSnapshot` and `LookupCache`.** For `resolve_object_location_locked` and `lookup_object_location`,
  change them in this part only if a command reaches them once per object. Otherwise record them in the report for
  ROADMAP.

**3. Tests:**
- **"The last entry wins" (C3):** an id with two records (a format-7 signature merge) returns the second, both before
  and after `rebuild_index_from_containers`;
- **the map agrees with a reverse scan:** a property test over random sequences of append, extend and replace;
- **red:** insert in reverse order, or skip the map update in `extend`, and a test fails. Show both.

**4. Measure (C2), against `main` before the part, on tmpfs:**
- `verify` and `bundle import` at 1,000, 10,000, 30,000 and 100,000 objects;
- lookup time for a missing id at 100 and at 100,000 objects;
- the index's resident memory at 100,000 objects: entries plus the map's capacity, or an RSS delta.

**Targets:**
- lookup within 2× of its cost at 100 objects;
- resident index no more than 2× today's;
- `verify` and `import` growing about linearly.

**5. Text:** the CHANGELOG entry, with the measured `verify` figures.

## Part 2 — sync stage (i): two syncs per object instead of seven (about 90 minutes)

**Why:** on disk, each object written costs seven syncs, counted from source (2A2 review). 10,000 small objects take
1–3 minutes to import; a 10,000-file `commit` took 71 s.

1. **Look for a recorded reason first.** Search for one behind a directory sync on *every* append in
   `durable_append_reporting_offset`, on all three platforms (`anchored/linux.rs`, `macos.rs`, `none.rs`). Read the RFCs
   too (102, 160, 162, 168) and the fsutil module docs. **If a reason exists, stop and report.**
2. **Sync the directory only when the append created the file.** Detect creation from the open itself, never from a
   length of zero.
3. **Hold the `ObjectStore` container lock once across a loop that writes many objects.**
   `write_object_under_held_lock` already exists; `archive import` uses it.
   - **Enumerate every such loop from source:** at least `bundle import`, `sync accept` and `commit`'s blob writes.
   - **Show the lock order is unchanged.** Today the container lock is a leaf (`object_store.rs:210`–`211`), so nothing
     may be acquired while it is held.
4. **Count the syncs per object, with a test instrument** (the failpoint hooks around each sync are a natural place).
   Expected: 7 before and 2 after. That count is the red control: with the change reverted, it reads 7.
5. **The crash property is unchanged:** each append is still synced before the next, so a crash leaves at most one
   torn tail. The existing F3 and failpoint tests pass unchanged; name them.
6. **Measure on the `/home` disk, against `main` before the part:** `bundle import` at 1,000 and 10,000 small objects,
   and a `commit` of 10,000 files.
7. **Text:** the CHANGELOG entry, with those figures.

**Measured in headless Chromium** (`/usr/bin/chromium`, `--headless=new --dump-dom`). A copy of the page, plus a probe
that prints each panel's `hidden` and computed `display`:

The two probe pages are in `.git-exclude/scratch/landing-tabs/`.

**G4, the fix:**
- **One rule near the top of the page's CSS:** `[hidden]{display:none !important}`. It covers this panel and any later
  element whose class sets `display`.
- **Without JavaScript, nothing changes:** only the script sets `hidden`, so both commands stay visible.
- **Correct the comment at `:468`–`:473`.** "Neither is hidden by any CSS rule" stays true, but say why the `[hidden]`
  rule exists.
