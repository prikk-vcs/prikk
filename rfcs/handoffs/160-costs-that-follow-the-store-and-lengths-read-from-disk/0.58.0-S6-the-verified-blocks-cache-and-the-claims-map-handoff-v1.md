## Part one: the verified-blocks cache

**What the cache is:** best-effort, and its doc says so ("a failure to write leaves fewer entries, never an error"). **That
gives the rule:**
1. **An entry may be present only for a Block that was replay-verified. Absence is always safe.** A missing entry costs a
   later re-verification, and a wrong entry would let an unverified Block anchor a derivation (RFC 159). Every option is
   judged against that sentence first.
2. **Who reads it inside a batch, and does any claim depend on an earlier claim's entry being on disk?** The fold anchors in
   memory (S2b), but the disk path after an abandoned plan reads the cache. **Say what a later claim's derivation reads,** and
   show that deferring the write cannot make it read an entry that is not there. If it can, that claim must use the batch's
   in-memory set.
3. **Crash behaviour:** a kill between claims leaves the cache without the ids not yet written. That is a cost (a later run
   re-verifies), never a wrong entry. Add the row to S2a's crash tests: row 2 or row 4, kill, re-run, the end state equals the
   corpus, and say what the cache holds.
4. **Concurrency:** two processes rewriting the file can lose each other's entries, which is safe by rule 1. **State it,** and
   say whether any writer can leave a wrong entry, for example by writing from a set it read before another process's
   replacement. If one can, stop and ask.

**The options to lay out, at least these:**
- **(i)** record the batch's ids once, at the end of the batch (or at its last publication);
- **(ii)** an appendable cache format: a new record version, readers accepting both, and a full rewrite only on compaction;
- **(iii)** keep the set per hold with S4's mechanism. The file is replaced by rename, so the identity changes on each own
  write, and the kept copy must take the new identity after its own write.

For each: the bytes read and written per claim at 250, 1,000 and 10,000, what a crash leaves, and the code it touches.
**Prefer the one with no format change if it meets the numbers.** A cache format change is cheap to make, but it is still a
second reader to keep.

## Part two: the batch keeps its claims map

`claims_by_block`, and what `parent_reached` and `refuse_if_order_ambiguous_among` derive from the stored claims, are built
**once per claim set**. That means once per batch, plus once per S3 refresh when the container grew (S3's
`refresh_claims`). They live in `SealBatchPlan` beside the claims. A claim stored mid-batch is still seen by the next
claim's check (S3's test `s3_a_claim_stored_mid_batch_is_seen_by_the_next_claim` keeps passing).
