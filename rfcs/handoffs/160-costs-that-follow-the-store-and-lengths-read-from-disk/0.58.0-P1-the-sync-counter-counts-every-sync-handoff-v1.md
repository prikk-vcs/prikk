## What is wrong today

**The counter (`fsutil/anchored/failpoints.rs`, `SYNC_CALL_COUNT`) increments only at the failpoint `Point`s that
`is_sync_point` names.** The syncs of the directory walk are not among them:
- `created_directory_parent_sync`;
- `observed_directory_parent_sync`;
- the parent syncs in `open_validated_child`.

So the counter reads 2 per object inside a held lock, where the kernel sees about 5:
- external review 037 §2.2;
- the architect's `strace -f -c` on main, 2026-11-12 (`~/.pgtmp/scope058-probe3.log`):
  - `bundle import` of 213 objects: 1,091 fsyncs;
  - `sync accept` of the same history: 1,058;
  - `commit` of 200 new files: 1,039.

**planeter's shape on the published 0.57.0** (`~/.pgtmp/scope058b/probe18.log`):
- `sync accept`: about 10 fsyncs per patch;
- `sync seal`: about 57 per claim.

**Read-only `status` and `verify` each make one fsync.**

## The rule (the conditions, owner-accepted)

1. **The counter counts at the primitive, not at a list of points.** Every call that reaches the platform's sync is
   counted, whoever calls it:
   - `File::sync_all` in `linux.rs`, `macos.rs` and `windows.rs`;
   - `Directory::sync`.

   **One counting site per primitive**, so a new caller cannot be missed. `is_sync_point` either goes away or only names
   failpoints, never what is counted. All syncs in `prikk-store` go through `fsutil` today (the architect grepped:
   `sync_all`, `F_FULLFSYNC` and `FlushFileBuffers` appear outside `fsutil` only in `doctor/tests.rs`). The report
   re-runs that grep.
2. **Test-only.** A release build pays nothing:
   - no atomic and no branch in a shipped binary;
   - `cfg(test)`, or a test-support feature that release builds do not enable.

   Say which, and show it from a release build: the symbol is absent, or the code compiles away.
3. **"A sync" means prikk's primitive.** That is `fsync` on Linux, `F_FULLFSYNC` on macOS (`fsutil/contract.rs:30`) and
   `FlushFileBuffers` on Windows. **`strace` witnesses Linux only, and the test's text says so.** The macOS and Windows
   counts are the primitive's calls, with no kernel witness. Do not word them as more.
4. **The counter agrees with `strace` per operation kind,** because agreement on one command is not agreement. On one
   fixture each, the counter's number for the store operation equals `strace -f -e trace=fsync,fdatasync`'s count for
   the binary doing the same thing. The operation kinds:
   - `commit`;
   - `seal`;
   - `bundle import`;
   - `sync accept`;
   - `sync seal`;
   - `archive import`;
   - the readers: `status`, `verify`, `log`.

   **Where they differ, the report names the difference and its source,** and the difference is fixed or explained.
   A difference no one can explain is a stop-and-ask. The `strace` side runs where `strace` exists. The suite does not
   require it: an agreement table in the report, and a test that pins the counter's numbers, are enough.
5. **The readers' sync is named.** For the one fsync that `status` and `verify` make, find the call, then either:
   - say in one comment why a reader needs it; or
   - remove it, if nothing needs it.

   It is the same rule for `log`. If removing it changes anything a test observes, stop and ask.
6. **The numbers become tests.** Pin them in `caller_tests/sync_count.rs` or beside it:
   - per object outside a held lock, and inside one at N = 1, 10, 100;
   - each operation kind's count on its fixture.

   These are P2's baseline. Today's `single_object_write_outside_a_held_lock_costs_five_syncs` and the held-lock loop's
   `3 + 2*N` will change when the walk's syncs are counted. Update them to the measured truth and say by how much.

## The red controls

- **Remove the counting from one primitive** (file, then directory). Name the assertions that go red.
- **Add a sync to a reader.** Its pin goes red.
