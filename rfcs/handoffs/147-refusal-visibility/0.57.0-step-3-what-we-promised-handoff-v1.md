## What is true today (measured by the architect on `1f314053`, 2026-11-09)

- **`log --format json`:** each block has `block_id`, `kind`, `parent_count`, `patch_count`, `patch_messages`,
  `previous_ref_state_id`, `ref_state_id`, `required_attestation_count`, `rollback_block`, `rollback_patch_count` and
  `update_seq`. There is no parent id and no sealer.
- **`verify --format json`:** the top-level keys are `active_sessions`, `schema_version`, `stages`,
  `unreached_objects` and `verdict`. There are no sealers, no item counts, no failed objects.
- **`branch create heads/f --from <block id>`** refuses: "--from ref … does not resolve to a published ref".
  `tag create --target <block id>` accepts the same id (stikk's reading: `tag.rs` `resolve_target_block`, `branch.rs`
  `resolve_published_target`).
- **`cat --path x.sh --output <file>` of a 0755 file** writes 0644.
- **`cat --path nope --format json`** prints the text refusal, not a `refusal-v1` document.
- **`sealed_by` is shipped** in `bundle preview` as "a plain list of signing key ids, reported but never trusted". Its
  per-signature outcomes are in a separate, additive `sealed_by_signatures` (`commands.md`, the `bundle preview`
  section).
- **`parent_block_ids` is the Block's own stored field, sorted by object id.** So a merge's parents carry no "first
  parent" order (`data-model-lifecycle.md`).

## Part S1: `branch create --from <block id>` (60 min, stop at 120)

Our promise (029 §2, 1.1): yes, for a block that a local branch or tag reaches. A received-only or unreached block is
refused by name, because publishing it as a local branch would bypass the trust checks `archive import --adopt`
makes.

1. **Case table first:**
   - a block reached from the current branch;
   - a block reached from another local branch;
   - a block reached from a tag only;
   - a received-only block;
   - an unreached block;
   - an id that is not a Block (a RefState, a patch);
   - an id that does not exist;
   - `--from` a ref, as today.
2. **Resolve the id through the point resolver other readers use** (RFC 153). Do not write a second one, and do not
   put lower-layer types in the upper resolver.
3. **The refusals name the block, why, and a typeable way forward:**
   - for a received-only block: `archive import --adopt`, or whatever is true. Measure it first;
   - for a non-Block: say what the id is.

   **Every refusal comes before the first write.**
4. **The RefState written** is the same as from a ref (stikk's reading, `branch.rs` `update_seq: 1`, no previous).
   Assert it.
5. **Tests through the binary for each row,** with red controls. `branch switch` to the new branch shows the block's
   files.

## Part S2: `log --format json` gains `parent_block_ids` and `sealed_by` (60 min, stop at 120)

Our promises: stikk 029 §4.3 (`parent_block_ids`); inklkunn §1 (each block's `sealed_by`: "the maintainer key ids its
seal records", "as recorded, not as trusted: it reads the same before and after `trust maintainer remove`"; "the same
field reaches `verify-report-v1` in the same release").

1. **`parent_block_ids`:** the Block's stored list, as stored. A root block has `[]`. The reference says the order is
   by object id and means nothing, so a consumer must not read a "first parent" from it. Keep `parent_count`.
2. **`sealed_by`:** the same shape and meaning as `bundle preview`'s `sealed_by`, a plain list of key ids. Measure
   first where a block's seal signatures are recorded (RFC 156: one object, several signers), and report every key id
   recorded. Test it:
   - **identical before and after `trust maintainer remove`** of one sealer (inklkunn's case);
   - with two sealers on one block;
   - for a rollback block.
3. **Additive within the current schema version,** as `active_sessions` was. Say in the report why no version bump is
   needed, from the schema's own rule.

The ROADMAP row adds a `publication_trust_issues` array (`{object_type, object_id, key_id, outcome}`).

## Part S4: `cat --output` applies the recorded mode, and `cat`'s refusals get `refusal-v1` (60 min, stop at 120)

Our promise (029 §4.5): `cat --output` applies the recorded mode, as `extract` does, and its refusals get `refusal-v1`.

1. **The mode through `extract`'s own function,** not a second one. Only the two modes prikk records, 0644 and 0755.
   - Nothing beyond those two is ever taken from received content.
   - With `--force` over an existing file, the mode is applied as well.
   - On Windows, the behaviour is whatever `extract`'s is. Say what it is.
2. **Inventory every refusal `cat` can give** (bad path, absent path, binary to a terminal, `--max-bytes`, `--output`
   exists, a point that does not resolve, a damaged object …).
   - Reuse an existing `refusal-v1` id wherever the meaning is the same; check the registry.
   - Add a new id only where none fits, and name each in the report.
   - **Measure the JSON id, not only the sentence:** the 0.56.0 lesson was `extract` saying `damaged-repository` in
     JSON while its text said "not damage".
3. **Tests:** the mode (0755 → 0755, 0644 → 0644, with and without `--force`), and each refusal's JSON document.

## Part S5a: discarding a sound queued patch, the design (60 min; a design report, no code)

Our promise (inklkunn §4): "it acts on a patch named exactly; it has `--plan-only`, and a recovery record so the
discard can be undone; it reports in the same shapes as the other repairs". The ROADMAP adds two requirements: it is
raced against ordinary writers, and it updates the worktree record's queued fold. **Its name must not be confusable
with `doctor --discard-damaged-commits`. It is chosen in this design step and shown to the owner.**

1. **Measure first:**
   - what a queued patch is on disk;
   - what references it (the active WAL, the worktree record's queued fold, a claim);
   - what `doctor --discard-damaged-commits` does and refuses, and why it refuses a sound patch.
2. **A case table:**
   - the last queued patch;
   - a middle one, with later patches depending on it;
   - a patch named by a claim;
   - a patch on another ref's queue;
   - a sealed patch;
   - an unknown id;
   - a crash at each write;
   - the undo after each.
3. **Two or three names, with the confusion each risks,** and your recommendation. The architect takes them to the
   owner.
4. **The undo:** what the recovery record holds, what command restores it, and that the restore is itself raced.
