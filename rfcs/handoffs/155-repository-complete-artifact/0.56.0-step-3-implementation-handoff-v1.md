## 3e — the claim walk, and `extract --claim` over a chain

- **One walk** (D4):
  - one map from block id to claims, built in one scan;
  - from the named claim back to a parent that is a **reachable** block (`block_is_sealed_or_received`);
  - a reachable block wins over a claim recognizing it.
- **What the walk records:** each link's signature outcome, and its structural failures:
  - `claim-chain-shared-block` (D1, including the exception for exactly one `sound` candidate);
  - `claim-chain-cycle`;
  - `claim-has-several-parents` at any link;
  - `claim-parent-not-sealed`.
- **Signatures (D2):**
  - `invalid` at any link, **the named claim included**, refuses `claim-signature-invalid`;
  - `unverifiable` proceeds.
- **Fold:** a link that does not fold refuses `claim-does-not-fold`, never `damaged-repository`.
- **Bound (D3):** the anchor's distance plus the chain's hops is checked against `MAX_ANCHOR_DISTANCE`, refusing
  `no-checkpoint-in-reach` and naming both numbers; `--allow-full-replay` overrides it.
- **`extract-report-v1`, additively:**
  - `chain[]`, root to foot, each entry `{claim_id, target_block_id, parent_block_ids, signature}`;
  - `chain_signature`, the weakest outcome;
  - the text form names each link, and prints "unverified" when the weakest is `unverifiable`.
- **Tests:** every row of 2B's case table, with hand-made claims for shared-block, cycle, merge mid-chain, invalid,
  unsigned, fold failure, and the bound. **Include the single-claim output changes:**
  - a forged claim refuses;
  - a held but unreached parent refuses;
  - a fold failure is classified.
- **Red controls:**
  - the signature check removed;
  - reachability replaced by existence;
  - the hop count left out of the bound.

### W1 — the worktree follows the current branch (a design report, no code)

**Measured on 0.55.0 by the architect** (`~/.pgtmp/stikk023m`, `~/.pgtmp/stikk023s`): after each of these commands, the
new tip's files are not in the worktree, and the user's next ordinary `commit` records `delete-file` for them:
- `merge --into <current branch>`;
- `archive import --adopt` onto the unpublished current branch;
- `sync seal <current branch> --claim …`;
- by reading, stikk 023 §3.1: `commit --ref <other>`, then `branch switch <other>`.

Once sealed, that commit undoes the merge or the delivery.

1. **The class, from source.** Name every command that moves the current branch's tip, or publishes it for the first
   time, with content not written from this worktree. Grep the ref publishers; do not stop at the four above. Measure
   each on a build of `main`.
2. **Is the worktree's baseline recorded?** That is the block or state the worktree was last written from (by `setup`,
   `branch switch`, `checkout`, or the user's own commits). Say where, or that it is not.
3. **The options:**
   - **(a)** each command writes the new tip's files into a **clean** worktree, and refuses before any write when the
     worktree is not clean;
   - **(b)** an invariant guard: **`commit` refuses when the current branch moved since the worktree was last written**,
     names the command that brings it up to date, and never authors the deletion of a file the worktree never held.
   - **The architect expects both:** (b) protects against every member, including future ones; (a) is the ordinary
     experience.
   - Say what each costs, and what "clean" means (`worktree-status` against which baseline).
4. **Edge cases:**
   - the unpublished current branch (the `--adopt` case);
   - queued, unsealed work for the current branch when another command moves it;
   - a crash between the ref write and the worktree write. Name which comes first, and what the next command sees.
5. **A case table** (command × worktree clean/dirty × today/proposed), the refusal ids, the text, and the CHANGELOG
   lines. Recommend; the architect rules.
