## Part S2a: the safety net, on today's code (90 min, stop at 180). The behaviour does not change

**Built and green before the fold exists, so that the fold is judged by tests written without it.**

1. **The corpus (condition 1), as S1 §6 designed it.**
   - **A generator test** builds each shape from deterministic seeds:
     - text edits;
     - large binaries (small in the committed corpus, for example 4 blocks of 64 KiB);
     - a merge in the history;
     - renames;
     - several refs;
     - a received checkpoint (a receiver pre-filled by `bundle import --adopt`);
     - a mid-batch refusal (a divergent claim at position k).
   - For each shape it builds the source, the artifact, the receiver, `sync accept` and `sync seal`.
   - **It records:**
     - the block ids and RefState ids;
     - the `sha256` of the receiver's ref log and pointer index;
     - `log --format json` (with the repository path removed);
     - the exit code and the `FAILED` line where there is one.
   - **Committed as a fixture at the commit S2a builds on.** The test asserts the fixture. A change to sealing output fails
     it, and the fixture is never regenerated to make a build pass. Say in the test's header that regenerating it needs
     the architect's ruling.
   - **The two-build check for the large shapes** (100 MiB of binaries; 1,000 claims in planeter's shape): a script, not a
     suite test. It runs the binary at this commit and the build, and compares the same records. Keep it beside the S1
     scripts, and run it in S2b.
2. **The five crash rows (condition 5), as real-kill tests.** Today no test kills a `sync seal`. Use S1's crash table: a
   3-claim batch onto the current branch, the process killed at the five points, through the binary. Use a test-support
   failpoint; the `PRIKK_PROBE_ABORT` shape from S1's probe worktree is fine, under `test-support` like P2b's pause hook.
   - **Each row asserts what S1 measured:** what is on disk, the exits of `status`, `verify` and `doctor`, and the next
     `sync seal` (after `unlock`) ending in the no-crash corpus's state.
   - **Row 5 asserts today's behaviour** (the re-run is a no-op and clears the marker; the worktree is behind). **S2b
     changes it** (below), and S2a's test is written so that S2b's change is one expected value.
3. **The refusal inventory as a checklist (condition 2).** S1 §3's table goes in the test module's header as the list
   S2b must keep. Every per-claim refusal there that has no test today gets one now, through the store, at the claim where
   it fires. S1 cites `seal_from_accepted/tests.rs` rows 1–11 for most of them. **Name any row without a test, and add
   it.**

**The red controls:**
- change one byte of a sealed output (for example, a RefState field) and the corpus goes red;
- kill at a point the table does not list, and say what the nearest row's test says.

**No CHANGELOG entry** (tests only).

## Part S2b: the fold (120 min, stop at 240)

**The rule** (S1 §5 (i)/(ii), ruled as one mechanism):
1. **The batch is folded once.**
   - The pre-batch state is derived once, anchored as RFC 159 already does for `AnchorSite::SealFromAccepted`.
   - Each claim's patches are then applied to one running state, in claim order.
   - **The batch simulation (a), which feeds the in-the-way check, and the per-claim loop (b) use the same running state
     and the same fold function.** Never two derivations of one batch.
2. **The running state is the nearest anchor, under RFC 159's rules,** never as an exception to them:
   - it is derived in this process from verified inputs;
   - each claim's Block is signed and recorded replay-verified as today;
   - an anchor that does not match its Block's recorded root is never used.

   Say in the code which rule each step meets.
3. **`CandidateDerivation::state`** is documented as test-only today. If production now reads it, rewrite that doc to say
   what production reads and why. If the running state lives behind a new function in `block_state.rs`, say that
   instead. **Either way there is one place, and its doc is true.**
4. **Refusals:** every row of the S2a checklist still fires, with the same message, at the same claim. **It may fire
   earlier, never later** (the S1 review, ruling 2). That includes a divergence found by the fold before the derived-Blob
   write at `block_state.rs:492`, which then becomes a refusal before any write. Name each one that moved.
5. **Crash row 5 changes** (architect's ruling, not objected to by the owner). A re-run that finds every claim already
   sealed **and the interrupted-materialization marker set** finishes the materialization: it writes the worktree from the
   ref, as `branch switch <ref>` would, then clears the marker, and says so in one line. It never clears the marker
   without materializing.
   - If the worktree is not clean against the marker's baseline, it refuses as today's in-the-way check does, naming the
     way out.
   - **The docs and the CHANGELOG** (`### Changed`) say it.

**It closes on the numbers.** Re-run S1's measurement on the build: the same scripts and shapes, base, noncur and nosim.
- **The binaries shape (100 MiB):** 8.5 GB of reads → about the history read once or twice. **Target: ≤ 300 MB.** Peak
  memory: (a)'s 114 MB → (b)'s level, about 12 MB. If either misses, say by how much and why.
- **Planeter's shape (250 and 1,000 claims):** derivation's share goes. The rest stays for S3–S5. **The expected total is
  about 81% of S1's**, so state the measured figure and the remaining families' bytes, per file, as S1 §2 does. That is
  S3's baseline.
- **fsyncs:** unchanged, or fewer. Never more.
- **The corpus** (S2a) is green. The two-build check on the large shapes is identical. The five crash tests pass, with
  row 5's new expected value.

**The red controls:**
- give (a) its own derivation back: the reads at 100 MiB return, and the test that holds "one fold" goes red (name it);
- break the fold order: the corpus goes red;
- make row 5 clear the marker without materializing: its test goes red.

**Docs:** the sync guide on crash row 5, and `durability-recovery.md` if it describes a `sync seal` re-run. **CHANGELOG:**
`### Changed`, with the measured reads before and after for both shapes.
