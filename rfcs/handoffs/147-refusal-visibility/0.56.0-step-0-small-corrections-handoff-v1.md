## 1. `log --ref <block id>` must never answer an empty success

**Measured on the published 0.55.0 binary** (inklkunn's report, reproduced by the architect):
- `prikk log --ref <64-hex block id> --format json` exits 0 with `"blocks": []`;
- `show`, `cat --ref` and `extract --block-id` accept the same id.

**The fix:**
- **Resolve `--ref` through the shared point resolver** (`ref_resolution.rs:171`, `resolve_point`) that `show`, `cat`
  and `tree` use, so a block id shows the history ending at that block. Say what `log` prints for a received block, and
  for an unreached one, consistently with those readers.
- **If resolving a block id is wrong for `log` in some respect you find, stop and report** with the reason. The minimum
  is a refusal naming the rule, as `diff` does ("is neither a ref name … nor a block id"). An empty success is never
  acceptable.
- **Grep every other reader that takes `--ref`** for the same empty answer, a rule over a class: `worktree-status`,
  `sync have`, and any others. Name each one, and its behaviour, in the report.
- **Tests:**
  - a block id gives its history, or refuses by name;
  - an unknown 64-hex id refuses by name;
  - an existing ref still works.
- **Red:** restore today's lookup, and the test fails on the empty answer.
- **Text:** `commands.md`'s `log` entry, and the CHANGELOG (`### Output changes`, since a script can see it).

## 2. A crashed writer's stale locks are named where the user looks

**Measured in the 0.55.0 round (2A2 review):** a `bundle import` killed mid-write can leave three stale locks:
`active.lock`, `received-index.lock` and `objects.lock`.
- The next writer says `lock conflict: … already exists` without naming `prikk unlock`.
- `doctor` exits 0 and names none of them.

**The fix:**
- **Every `lock conflict` refusal names the command that lists and clears locks:** `prikk unlock` to list them, and
  `prikk unlock --lock <path>` to clear one once the process that held it is confirmed gone. Keep the existing advisory
  wording about liveness. Find every site that produces a lock conflict, not just one.
- **`doctor` lists each held lock** with its kind, its recorded pid and the same liveness wording `unlock` uses, as an
  informational line, **not a warning**. A lock held by a running process is normal, and `doctor` must not report a
  healthy concurrent writer as a problem.
- **Tests:**
  - a real killed writer, reusing 0.55.0's real-kill seam: the next writer's error names `prikk unlock`, and `doctor`
    lists all three locks;
  - a lock held by a live process is listed as informational, and `doctor`'s exit code is unchanged.
- **Red:** remove the new line from the error, and the test fails.
- **Text:**
  - `concurrency-locking.md`'s lock-conflict paragraph (line 117 or so);
  - `troubleshooting.md` if it covers lock conflicts;
  - the CHANGELOG.
